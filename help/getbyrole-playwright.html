Playwright Locators

getByRole() in Playwright

Playwright's recommended user-facing locator — find elements by their ARIA role, accessible name, and state instead of by CSS structure or XPath.

@playwright/test v1.27+ page / locator / frameLocator ARIA role + accessible name Returns a Locator Beginner → Advanced

01What Is It?

getByRole() is a Playwright locator method that finds elements by their ARIA role — and optionally by their accessible name and state attributes such as checked, disabled, expanded, pressed, and selected. It is the first choice in Playwright's recommended locator strategy because it mirrors how assistive technology and users perceive the page, not how the DOM happens to be structured.

await page.getByRole('button', { name: 'Submit' }).click();

It was introduced in Playwright v1.27 as part of the "user-facing locators" family, alongside getByLabel(), getByText(), getByPlaceholder(), getByAltText(), getByTitle(), and getByTestId().

Why it exists

CSS and XPath selectors describe implementation: a class name, a tag hierarchy, a DOM position. Tests written that way break whenever a developer refactors markup, even when the page's meaning and behaviour are unchanged. Role-based locators describe intent — "the Submit button" — so they survive those refactors.

Playwright does not invent roles: it matches the ARIA role from the W3C ARIA specification, plus the implicit roles that HTML elements already have under HTML-AAM. That means a plain <button>Submit</button> is matched by getByRole('button', { name: 'Submit' }) with no attributes added.

What problem it solves

  • Non-brittle tests — renaming a CSS class or wrapping an element in a new <div> does not break a role locator.
  • Readable tests — the code states which user-facing control it interacts with.
  • Accessibility feedback — if you cannot locate a control by role and name, a screen reader user may not be able to reach or identify it either.
  • Consistency — the same locator works across browsers, because the role mapping is standardised.

Where it is commonly used

  • Clicking buttons, links, tabs, menu items, and checkboxes.
  • Filling form fields where the role is textbox, combobox, or searchbox.
  • Asserting on headings and their levels.
  • Scoping work inside a table, row, list, or dialog.
  • Anywhere a test needs to interact with the page as a user would.

When to use it

Reach for getByRole() first. Fall back to getByLabel() or getByPlaceholder() for unlabelled form fields, getByText() for static content, and getByTestId() when no meaningful role or text exists or when the element is deliberately anonymous to assistive technology.

Not an accessibility audit Playwright's own documentation is explicit: the role locator does not replace accessibility audits and conformance tests. It gives early feedback about ARIA usage, but tools such as axe and manual screen reader testing are still required for real coverage.
It returns a Locator, not a Promise getByRole() is synchronous — do not await the call itself. Await the action or assertion: await page.getByRole('button').click(). The returned locator re-queries the DOM on every use, so it always reflects the current page.

02Syntax

Basic form

page.getByRole(role, options)

The three entry points

// Whole page
await page.getByRole('button', { name: 'Submit' }).click();

// Scoped to another locator - searches only inside that element
await page.getByRole('dialog').getByRole('button', { name: 'Cancel' }).click();

// Inside an iframe
await page.frameLocator('#checkout').getByRole('button', { name: 'Pay' }).click();

Breaking down the parts

PartMeaning
roleRequired. One of the ARIA roles Playwright supports, e.g. button, link, textbox, heading, checkbox, dialog. The TypeScript type restricts it to that union, so a typo fails to compile; at runtime an unrecognised role is not an error — it matches nothing and the next action times out.
optionsOptional object. The most-used key is name; the rest filter by state (checked, disabled, expanded, level, pressed, selected) or change matching (exact, includeHidden, description).
return valueA Locator. It is lazy: nothing is queried until you act on it or assert against it.
auto-waitingInherited from locators. Actions wait for the element to be attached, visible, stable, enabled, and receiving events — no manual sleeps.
strict modeIf the locator matches more than one element, actions and assertions throw a strict-mode violation. Narrow the locator instead of relying on "first match".

How name is matched

The name option is compared against the element's accessible name — the same value computed from aria-label, aria-labelledby, an associated <label>, the element's text content, or alt text.

InputBehaviour
name: 'Submit'Case-insensitive substring match; surrounding whitespace is trimmed.
name: 'Submit', exact: trueCase-sensitive, whole-string match (still trims whitespace).
name: /submit/iRegular expression; exact is ignored when a RegExp is used.
 
<button>Submit order</button>

page.getByRole('button', { name: 'Submit' });          // matches (substring)
page.getByRole('button', { name: 'Submit', exact: true }); // no match
page.getByRole('button', { name: /^submit order$/i }); // matches
Substring matching surprises Because the default is a substring match, name: 'Save' also matches "Save as draft" and "Auto-save". When several similar controls exist, prefer a regex or exact: true rather than reaching for .first().

The underlying role selector

getByRole() wraps Playwright's role= selector engine. The two forms below are equivalent; the API form is preferred for readability and type safety.

page.getByRole('button', { name: 'Submit' });
page.locator('role=button[name="Submit"]');

Roles come from two places An explicit role="..." attribute always wins. 05Detailed Reference

Expand an entry for its purpose, parameters, a runnable example, and the pitfalls worth knowing.

getByRole()
Purpose
Creates a locator that finds elements by ARIA role, optionally filtered by accessible name and state.
Syntax
page.getByRole(role, options)
Parameters
role (required) — a supported ARIA role, e.g. 'button', 'link', 'heading'. options (optional) — name, exact, checked, disabled, expanded, level, pressed, selected, includeHidden, description.
Return / Result
A Locator — lazy, auto-waiting, and re-evaluated on each use. It is not a Promise.
Example
<h1>Sign up</h1>
<label><input type="checkbox" /> Subscribe</label>
<button>Submit</button>

// test
await expect(page.getByRole('heading', { name: 'Sign up' })).toBeVisible();
await page.getByRole('checkbox', { name: 'Subscribe' }).check();
await page.getByRole('button', { name: /submit/i }).click();
Expected Result
The heading assertion passes, the checkbox becomes checked, and the click hits the Submit button — all without any test ids or CSS classes.
Common Usage
The default locator for buttons, links, inputs, headings, and landmarks throughout a test suite.
Important Notes
Strict mode applies: matching several elements makes actions throw. An unknown role does not throw — it matches nothing and the action times out, so check the role name first when debugging. Elements hidden from the accessibility tree are skipped unless includeHidden: true is set.
The name option
Purpose
Disambiguates by the element's accessible name, so every locator reads like a user instruction.
Syntax
page.getByRole('button', { name: 'Submit order' })
page.getByRole('button', { name: /submit/i })
Parameters
A string (case-insensitive substring by default, whitespace-trimmed) or a RegExp (tested against the name; exact is ignored).
Return / Result
Narrows the role match to elements whose computed accessible name matches.
Example
<button aria-label="Close dialog">×</button>

await page.getByRole('button', { name: 'Close dialog' }).click();
Expected Result
The icon-only button is found via its aria-label, even though it has no visible text.
Common Usage
Almost every role locator — passing a name is what makes strict mode workable.
Important Notes
The name must come from somewhere accessible: text content, aria-label, aria-labelledby, a <label>, or alt. A title tooltip is a weak fallback and should not be relied on. Watch out for substring matches such as 'Save' also matching "Save as".
exact
Purpose
Switches name and description matching from "case-insensitive substring" to whole-string and case-sensitive.
Syntax
page.getByRole('link', { name: 'Docs', exact: true })
Parameters
Boolean. Defaults to false (added in v1.28).
Return / Result
Only elements whose name equals the string exactly (whitespace trimmed) match.
Example
<a href="/docs">Docs</a>
<a href="/docs/api">Docs API</a>

await page.getByRole('link', { name: 'Docs', exact: true }).click(); // first only
Expected Result
Only the "Docs" link matches; "Docs API" is excluded, so no strict-mode violation occurs.
Common Usage
Whenever short names overlap with longer ones, such as "Save" / "Save as" or "Login" / "Login help".
Important Notes
It is ignored when name is a RegExp — use anchors there instead (/^Docs$/). Exact matching still trims leading and trailing whitespace, so line breaks in markup will not break it.
level
Purpose
Matches the heading (or list item / row / tree item) depth, so tests can assert document structure.
Syntax
page.getByRole('heading', { level: 2 })
Parameters
A number, matched against aria-level. For <h1>–<h6> the level defaults to the tag's number.
Return / Result
Only headings at that level match — both native <h2> and <div role="heading" aria-level="2">.
Example
await expect(page.getByRole('heading', { level: 1 })).toHaveCount(1);
await expect(page.getByRole('heading', { name: 'Billing', level: 2 })).toBeVisible();
Expected Result
The assertions confirm exactly one h1 exists and that the Billing section heading is an h2.
Common Usage
Structural smoke tests, SEO/outline checks, and disambiguating repeated headings.
Important Notes
Without level, getByRole('heading') matches headings at every level. Level is valid for heading, listitem, row, and treeitem.
checked
Purpose
Filters checkboxes, radios, and switches by their checked state.
Syntax
page.getByRole('checkbox', { name: 'Terms', checked: true })
Parameters
Boolean — true for checked, false for unchecked. It reads aria-checked or the native <input type=checkbox|radio> state.
Return / Result
Only controls in the requested state match.
Example
await expect(page.getByRole('checkbox', { name: 'Terms', checked: true })).toBeVisible();
await expect(page.getByRole('checkbox', { name: 'Terms', checked: false })).toBeHidden();
Expected Result
The first assertion passes only if Terms is already ticked; the second confirms the unchecked variant is gone.
Common Usage
Asserting persisted form state, filter panels, and toggle switches.
Important Notes
checked takes a boolean only — there is no "mixed" value for the indeterminate state. For assertions prefer toBeChecked(), which retries; a bare locator with checked: true matched against nothing fails immediately.
disabled
Purpose
Distinguishes enabled from disabled controls — useful for asserting that a form blocks submission until valid.
Syntax
page.getByRole('button', { name: 'Pay', disabled: true })
Parameters
Boolean. Reads aria-disabled or the native disabled attribute.
Return / Result
Only controls in the requested enabled/disabled state match.
Example
await expect(page.getByRole('button', { name: 'Pay', disabled: true })).toBeVisible();
await page.getByRole('textbox', { name: 'Card number' }).fill('4242 4242 4242 4242');
await expect(page.getByRole('button', { name: 'Pay', disabled: false })).toBeEnabled();
Expected Result
The Pay button starts disabled and becomes enabled once the card field is filled.
Common Usage
Validation flows, wizard gating, and permission-based UI.
Important Notes
Uniquely, disabled is inherited through the DOM hierarchy — a control inside a disabled <fieldset> is treated as disabled. Prefer toBeEnabled()/toBeDisabled() for assertions so they retry.
expanded
Purpose
Matches disclosure controls and comboboxes by their open/closed state.
Syntax
page.getByRole('button', { name: 'Filters', expanded: false })
Parameters
Boolean, matched against aria-expanded.
Return / Result
Only elements whose expanded state matches are returned.
Example
const toggle = page.getByRole('button', { name: 'Filters' });
await expect(toggle).toHaveAttribute('aria-expanded', 'false');
await toggle.click();
await expect(page.getByRole('button', { name: 'Filters', expanded: true })).toBeVisible();
Expected Result
The button starts collapsed and is matched as expanded after the click.
Common Usage
Accordions, hamburger menus, filter drawers, and comboboxes.
Important Notes
Only matches elements that actually expose an expanded state; if the widget never sets aria-expanded, neither true nor false will match. Asserting the attribute with toHaveAttribute is often clearer than swapping locators.
pressed
Purpose
Matches toggle buttons by their aria-pressed state.
Syntax
page.getByRole('button', { name: 'Bold', pressed: true })
Parameters
Boolean, matched against aria-pressed.
Return / Result
Only toggle buttons in the requested state match.
Example
const bold = page.getByRole('button', { name: 'Bold' });
await bold.click();
await expect(bold).toHaveAttribute('aria-pressed', 'true');
Expected Result
The formatting button reports itself as pressed after being clicked.
Common Usage
Rich-text editor toolbars and any button that stays "on".
Important Notes
Applies to toggle buttons, not to checkboxes or switches — use checked for those. A button that reports aria-pressed must change it on activation; a static value misleads assistive technology.
selected
Purpose
Matches the active item in a set — the chosen tab, option, row, or tree item.
Syntax
page.getByRole('tab', { selected: true })
Parameters
Boolean, matched against aria-selected.
Return / Result
Only items in the requested selection state match.
Example
await expect(page.getByRole('tab', { selected: true })).toHaveText('Overview');
await page.getByRole('tab', { name: 'Billing' }).click();
await expect(page.getByRole('tab', { selected: true })).toHaveText('Billing');
Expected Result
Exactly one tab is selected at a time, and selecting Billing moves the selection.
Common Usage
Tab widgets, single-select listboxes, and selected grid rows.
Important Notes
If the widget marks the active tab with a class instead of aria-selected, this option finds nothing — which is itself a useful accessibility signal. Native <select> options use the selected property/attribute rather than aria-selected.
includeHidden
Purpose
Opts in to elements that are excluded from the accessibility tree, such as visually hidden or aria-hidden content.
Syntax
page.getByRole('button', { name: 'Skip', includeHidden: true })
Parameters
Boolean. Defaults to false: only non-hidden elements, as defined by ARIA tree exclusion, are matched.
Return / Result
Hidden elements become eligible to match.
Example
<button style="display:none">Skip navigation</button>

await expect(page.getByRole('button', { name: 'Skip navigation' })).toBeHidden();          // not matched
await expect(page.getByRole('button', { name: 'Skip navigation', includeHidden: true })).toBeAttached();
Expected Result
The hidden button is invisible to the default locator but found when hidden elements are included.
Common Usage
Testing collapsed content, off-screen templates, and elements revealed only by CSS.
Important Notes
This is a debugging and edge-case tool. A control that is genuinely unreachable for assistive technology is usually a bug, not something to work around — prefer fixing the markup, or getByTestId() when the element is intentionally anonymous.
description
Purpose
Matches on the accessible description — supplementary help text rather than the name.
Syntax
page.getByRole('textbox', { description: 'At least 12 characters' })
Parameters
A string (case-insensitive substring by default, honouring exact) or a RegExp. Added in v1.60.
Return / Result
Narrows the match by the description computed from aria-describedby, aria-description, or title.
Example
<input aria-label="Password" aria-describedby="pwd-hint" />
<p id="pwd-hint">At least 12 characters.</p>

await page.getByRole('textbox', { description: 'At least 12 characters' }).fill('correct horse battery staple');
Expected Result
The password field is located by its hint text rather than its label.
Common Usage
Targeting fields with identical labels but different help text, and asserting hints are wired up.
Important Notes
Requires Playwright v1.60 or newer. For most cases name is the better discriminator; reach for description when the name alone is genuinely ambiguous.
.filter()
Purpose
Narrows an existing locator by text or by a contained/absent element — the standard way to pick one row, card, or list item.
Syntax
locator.filter({ hasText, hasNotText, has, hasNot, visible })
Parameters
hasText / hasNotText (string = case-insensitive substring, or RegExp) and has / hasNot (a relative locator, which must point inside the outer element).
Return / Result
A narrower Locator; filters can be chained.
Example
await page
  .getByRole('listitem')
  .filter({ hasText: 'Product 2' })
  .getByRole('button', { name: 'Add to cart' })
  .click();
Expected Result
The Add to cart button is clicked only inside the list item containing "Product 2".
Common Usage
Tables and lists — "the button in the row that has this text".
Important Notes
The inner locator must be relative to the outer one and belong to the same frame; an absolute locator or a FrameLocator inside has will not work. Chaining getByRole() after filter() is usually cleaner than passing a complex filter.
.first() / .nth() / .last() / .and() / .or()
Purpose
Resolve and combine multiple matches without weakening the locator's meaning.
Syntax
locator.first()        locator.nth(2)       locator.last()
locator.and(otherLocator)                  locator.or(otherLocator)
Parameters
nth() takes a zero-based index. and()/or() take another locator.
Return / Result
A Locator that resolves to one element (first/nth/last) or to locators satisfying both/ either condition.
Example
await expect(page.getByRole('listitem')).toHaveCount(5);
await page.getByRole('listitem').nth(2).click();

const save = page.getByRole('button', { name: 'Save' }).or(page.getByRole('button', { name: 'Update' }));
await save.click();
Expected Result
The third list item is clicked, and Save-or-Update resolves whichever button the UI presents.
Common Usage
Lists where an index is meaningful, and UIs whose button label varies by state.
Important Notes
.first() is a smell when it is only there to silence a strict-mode violation — that usually means the locator is not specific enough. and() requires v1.34+. Prefer an explicit toHaveCount() assertion before indexing so failures are diagnosable.
toHaveRole() & toHaveAccessibleName()
Purpose
Assert the same semantics that getByRole() locates by, turning an accessibility check into a test assertion.
Syntax
await expect(locator).toHaveRole(role);
await expect(locator).toHaveAccessibleName(name);
Parameters
The expected role string, or the expected name (string or RegExp). Both auto-retry until the assertion passes or the timeout expires.
Return / Result
Passes or fails with a diff showing the actual role/name.
Example
await expect(page.getByTestId('save')).toHaveRole('button');
await expect(page.getByTestId('close')).toHaveAccessibleName('Close dialog');
await expect(page.getByTestId('hint')).toHaveAccessibleDescription(/12 characters/);
Expected Result
The custom elements are proven to expose the intended semantics, even though they are located by test id.
Common Usage
Guarding custom components against ARIA regressions, and documenting intent in a readable way.
Important Notes
These are assertions, not locators — they need an existing element to check. They are a complement to getByRole(), not a replacement for an accessibility audit.
Debugging: highlight(), count(), ariaSnapshot()
Purpose
Work out what a role locator actually matches before committing to it.
Syntax
await locator.highlight();
await locator.count();
console.log(await page.locator('body').ariaSnapshot());
Parameters
None required. highlight() draws an overlay (added v1.20); ariaSnapshot() accepts optional depth/mode (added v1.49).
Return / Result
count() returns a number, ariaSnapshot() returns a YAML string of the accessibility tree.
Example
// How many matches? (diagnose strict-mode failures)
console.log(await page.getByRole('button').count());

// What roles and names does the page expose?
console.log(await page.locator('main').ariaSnapshot());

// Visually confirm the match in headed mode
await page.getByRole('button', { name: 'Submit' }).highlight();
Expected Result
count() prints the number of matches, the snapshot lists roles and accessible names, and the highlight outlines the element on screen.
Common Usage
Writing new locators, diagnosing timeouts, and reviewing a page's accessibility structure.
Important Notes
Remove highlight() before committing. The Playwright Inspector (PWDEBUG=1) and npx playwright codegen can also pick locators interactively.

06Practical Examples

Example 1 — Basic Usage

The simplest possible role locator: click a button by its visible text.

import { test, expect } from '@playwright/test';

test('basic role locator', async ({ page }) => {
  await page.goto('https://example.com/login');

  await page.getByRole('button', { name: 'Log in' }).click();

  await expect(page.getByRole('heading', { name: 'Welcome' })).toBeVisible();
});

No CSS class, no test id, no XPath. The button is found because the browser exposes it with the button role and the accessible name "Log in".

Example 2 — Real-World Usage: a login form

<form>
  <label for="email">Email</label>
  <input id="email" type="email" required />

  <label for="password">Password</label>
  <input id="password" type="password" required />

  <label><input type="checkbox" /> Remember me</label>

  <button type="submit">Sign in</button>
</form>
test('user can sign in', async ({ page }) => {
  await page.goto('/login');

  await page.getByRole('textbox', { name: 'Email' }).fill('ada@example.com');
  await page.getByRole('textbox', { name: 'Password' }).fill('s3cret');
  await page.getByRole('checkbox', { name: 'Remember me' }).check();
  await page.getByRole('button', { name: 'Sign in' }).click();

  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
});

Every line describes what a user does. The password field is a textbox even though its type is password, because that is the role browsers expose.

Example 3 — Multiple Functions: a table with row scoping

Combining getByRole() with filter(), count(), and assertions.

<table>
  <thead><tr><th>Product</th><th>Price</th><th></th></tr></thead>
  <tbody>
    <tr><td>Product 1</td><td>$10</td><td><button>Add to cart</button></td></tr>
    <tr><td>Product 2</td><td>$20</td><td><button>Add to cart</button></td></tr>
  </tbody>
</table>
test('add a specific product to the cart', async ({ page }) => {
  await page.goto('/shop');

  const rows = page.getByRole('row');
  await expect(rows).toHaveCount(3);            // 1 header + 2 body rows

  const product2 = rows.filter({ hasText: 'Product 2' });
  await product2.getByRole('button', { name: 'Add to cart' }).click();

  await expect(page.getByRole('status')).toHaveText('1 item in cart');
  await expect(page.getByRole('link', { name: /cart/i, exact: false })).toHaveText(/1 item/);
});

filter() narrows to one row, and the nested getByRole() scopes the button search to that row — so "Add to cart" being duplicated no longer causes a strict-mode violation.

Example 4 — Negative Scenario: strict mode violation

A locator that matches several elements fails loudly. Here, three buttons share the substring "Save".

<button>Save</button>
<button>Save as draft</button>
<button>Save and publish</button>
await page.getByRole('button', { name: 'Save' }).click();
// Error: strict mode violation: getByRole('button', { name: 'Save' }) resolved to 3 elements

Why it fails: name is a case-insensitive substring match by default, so all three buttons qualify. The fix is to make the locator specific rather than hiding the ambiguity:

await page.getByRole('button', { name: 'Save', exact: true }).click();
// or target a distinct name
await page.getByRole('button', { name: 'Save and publish' }).click();
Do not "fix" it with .first() .first() silences the error but makes the test depend on DOM order, which is exactly the brittleness role locators exist to remove. If the ambiguity is real — three identical "Delete" buttons in a table — scope with filter() instead.

Example 5 — Advanced Usage: options, regex, and state

<button aria-expanded="false" aria-controls="menu">Account</button>
<ul id="menu" hidden><li><a href="/profile">Profile</a></li></ul>

<h1>Dashboard</h1>
<h2>Billing</h2>

<button aria-pressed="false">Bold</button>

<div role="tablist">
  <button role="tab" aria-selected="true">Overview</button>
  <button role="tab" aria-selected="false">Billing</button>
</div>
test('advanced role locators', async ({ page }) => {
  await page.goto('/dashboard');

  // Collapsed disclosure -> open it, then assert the state flipped
  const account = page.getByRole('button', { name: 'Account' });
  await expect(account).toHaveAttribute('aria-expanded', 'false');
  await account.click();
  await expect(page.getByRole('button', { name: 'Account', expanded: true })).toBeVisible();
  await page.getByRole('link', { name: 'Profile' }).click();

  // Structural assertions with level
  await expect(page.getByRole('heading', { level: 1 })).toHaveCount(1);
  await expect(page.getByRole('heading', { name: 'Billing', level: 2 })).toBeVisible();

  // Toggle button state
  const bold = page.getByRole('button', { name: 'Bold' });
  await bold.click();
  await expect(page.getByRole('button', { name: 'Bold', pressed: true })).toBeVisible();

  // Exactly one selected tab, matched by regex
  await expect(page.getByRole('tab', { selected: true })).toHaveText(/overview/i);
  await page.getByRole('tab', { name: /^billing$/i }).click();
  await expect(page.getByRole('tab', { selected: true })).toHaveText(/billing/i);
});

State options (expanded, pressed, selected) let assertions read as plain English, and level turns heading structure into a testable contract. Where the state flips, asserting the accessible name with a regex keeps the locator stable across both states.

09Best Practices

  1. Reach for getByRole() first. Playwright's documented order is role → label/placeholder/text → test id. Only move down when the higher option genuinely does not exist.
  2. Always pass a name when the role alone is ambiguous. Role plus name is what makes strict mode useful rather than annoying.
  3. Fix the page, not the locator. If a control cannot be located by role and name, assistive technology probably cannot identify it either. Prefer correcting the markup over adding a test id.
  4. Scope instead of indexing. Chain from a container (dialog.getByRole(...)) and use filter() for rows and cards; a bare .nth() couples the test to DOM order.
  5. Use exact: true or a regex when names overlap. "Save", "Save as", and "Save and publish" should not rely on substring luck.
  6. Assert state with assertions, not locators. toBeChecked(), toBeEnabled(), toHaveAttribute('aria-expanded', 'true') retry and produce clear diffs; state-filtered locators fail instantly.
  7. Assert counts before indexing. await expect(rows).toHaveCount(5) turns an index error into a readable failure.
  8. Keep locators lazy. Store a locator in a variable and reuse it — do not resolve values with count() or textContent() and then assert on the plain value, which loses retry-ability.
  9. Never hard-code waits. Role locators auto-wait and retry, so waitForTimeout only makes the suite slower and flakier.
  10. Prefer one locator per concept. Extract repeated ones into small helpers or page objects, and give them a .describe() so traces and reports are readable.
  11. Use count(), highlight(), ariaSnapshot(), and the Inspector to develop locators. Diagnose strict-mode violations rather than suppressing them.
  12. Complement roles with real accessibility testing. Role locators give early feedback, but axe, keyboard-only runs, and screen reader checks are still required.

10Interview Questions

Beginner Questions

1. What does getByRole() do?
It creates a locator that finds elements by their ARIA role, optionally narrowed by the accessible name and by state attributes such as checked, disabled, expanded, pressed, and selected. It is Playwright's recommended first-choice locator.
2. Does <button>Submit</button> need a role attribute for getByRole('button') to find it?
No. HTML elements have implicit ARIA roles mapped by HTML-AAM, so <button> already has the button role. Adding role="button" would be redundant, and ARIA guidance advises against duplicating implicit roles.
3. Why is getByRole() preferred over a CSS selector?
It describes user intent rather than implementation. CSS selectors break when classes or DOM structure change, while role locators keep working as long as the element's semantics stay the same. They also surface accessibility problems: if a control has no role or no accessible name, the locator fails.
4. What does the name option match against?
The element's accessible name — computed from aria-label, aria-labelledby, an associated <label>, the element's own text content, or alt text. By default it is a case-insensitive substring match with whitespace trimmed.
5. Should you await page.getByRole('button')?
No. getByRole() returns a Locator synchronously — it is lazy and does not query the DOM until used. Await the action or assertion instead: await page.getByRole('button').click().

Intermediate Questions

6. What happens when a role locator matches more than one element?
Strict mode raises an error listing the matches. Playwright deliberately refuses to guess. The fix is to make the locator more specific — add name, use exact: true or a regex, or scope with a chained locator and filter() — not to bolt on .first().
7. How do you locate a level-2 heading, including one built from a div?
page.getByRole('heading', { level: 2 }). It matches native <h2> and <div role="heading" aria-level="2">, because level is compared against the computed aria-level.
8. How would you click the Delete button in the row containing "Ada"?
Scope by row and filter by text, then chain: page.getByRole('row').filter({ hasText: 'Ada' }).getByRole('button', { name: 'Delete' }).click(). The inner locator is relative to the filtered row, so it avoids both DOM-order dependence and strict-mode violations.
9. Why might getByRole('button', { name: 'Save' }) throw even though only one button visibly says "Save"?
Because name is a substring match by default, so "Save as draft" and "Auto-save" also match. Use exact: true or a regex such as /^Save$/.
10. When would you use includeHidden: true, and why is it usually a last resort?
When you must interact with elements excluded from the accessibility tree — collapsed content, off-screen templates, or elements hidden with aria-hidden. It is a last resort because such elements are typically unreachable for assistive technology; if a real control is hidden, the markup is usually at fault, and getByTestId() is the better way to target intentionally anonymous elements.

Advanced Questions

11. How does getByRole() relate to the role= selector engine, and what does that imply?
getByRole() is a typed wrapper over the role= selector: page.getByRole('button', { name: 'Submit' }) is equivalent to page.locator('role=button[name="Submit"]'). Playwright implements the ARIA role, attribute, and accessible-name specifications itself rather than asking the browser, which is why behaviour is consistent across browsers — and why it can differ in edge cases from a specific screen reader's interpretation.
12. Distinguish name, description, and exact.
name matches the accessible name — the label spoken when focus lands. description (v1.60+) matches the accessible description, i.e. supplementary help from aria-describedby or similar. exact (v1.28+) switches both from case-insensitive substring to whole-string, case-sensitive matching, and is ignored when a RegExp is supplied.
13. Why is disabled special among the state options?
It is inherited through the DOM hierarchy — a control inside a disabled <fieldset> is treated as disabled even if the control itself has no disabled attribute or aria-disabled. The other state options are evaluated on the element itself.
14. Your role locator times out. How do you diagnose it systematically?
First check await page.getByRole(role).count() to see whether the role matches anything at all. Then dump the tree with await page.locator('body').ariaSnapshot() to read the actual roles and accessible names. Use highlight() in headed mode to confirm visually, and PWDEBUG=1 or codegen to pick locators interactively. Common root causes: a mistyped role (which matches nothing instead of erroring), a name that does not exist (no label/aria-label), an implicit role you assumed wrongly, an element hidden from the accessibility tree, or content inside an iframe that needs frameLocator().
15. Does a passing role-locator suite prove the app is accessible?
No. Role locators verify that the elements your tests touch have roles, names, and states — a narrow slice of accessibility. They say nothing about colour contrast, focus order, keyboard operability, zoom, motion, or reading order. Use them for early feedback, then add axe-based checks and manual keyboard plus screen reader testing for genuine coverage.

13Key Takeaways

  • getByRole() is Playwright's recommended default locator: it matches ARIA role, accessible name, and state, so tests read like user intent instead of DOM structure.
  • Introduced in v1.27; exact arrived in v1.28 and the description option in v1.60.
  • HTML elements already carry implicit roles, so <button>, <a href>, and <h2> need no ARIA to be located by role.
  • It returns a Locator, not a Promise — never await the call itself.
  • name is a case-insensitive substring match by default; use exact: true or a regex when names overlap.
  • Strict mode makes ambiguous locators fail. Fix the ambiguity with name, scoping, or filter() — not with .first().
  • State options (checked, disabled, expanded, pressed, selected) and level express the UI's condition directly in the locator.
  • Hidden elements are excluded by default; includeHidden: true exists but usually signals a markup problem.
  • Chain from a container and use filter() to reach one row or card — robust tests never depend on DOM order.
  • Role locators give early accessibility feedback, but they are not an accessibility audit: pair them with axe and manual keyboard/screen reader checks.
