Assertion Reference

expect Functions in JavaScript / Playwright

Assertions used to verify expected conditions in Playwright tests — from auto-retrying web-first matchers to generic value checks.

@playwright/test JavaScript Auto-retrying Beginner → Advanced

01What Is It?

expect is the assertion function exported by @playwright/test. It checks whether a value or a page element matches what you expect, and it fails the test when it does not.

Playwright's expect exists to solve two different problems:

  • Verifying application state — "is this button visible?", "does this heading contain 'Welcome'?", "did the URL change?"
  • Verifying plain values — "is this array length 3?", "does this object equal that one?", "did this function throw?"

Why it exists

Web UIs are asynchronous. Elements appear, disappear, and change after network calls. A traditional assertion that runs once would fail flakily if it checked a millisecond too early. Playwright's web-first assertions solve this by auto-retrying the check until it passes or a timeout is reached.

What problem it solves

  • Flaky tests — constant retrying removes the need for manual sleep calls.
  • Readable tests — await expect(page.getByRole('button')).toBeVisible() reads like plain English.
  • Clear failures — when an assertion fails, Playwright prints the expected value, the actual value, and (for locators) the element it looked at.

Where it is commonly used

  • End-to-end UI tests written with the Playwright Test runner.
  • Component tests via Playwright's experimental component testing.
  • API tests, using the built-in request fixture and toBeOK().

When a tester should use it

Use expect whenever you state a claim about the application. If a step in your test is "the page should show X", that statement belongs in an expect. Verification steps are the whole point of an automated test — without assertions, a test only proves that no exception was thrown.

Two kinds of expect Playwright's expect combines the generic matchers from the Jest expect library (no retry) with Playwright's own web-first matchers (auto-retry). Knowing which is which is the single most important concept on this page.

02Syntax

Basic form

await expect(locator).toBeVisible();

Broken down:

TokenMeaning
expectThe assertion entry point, imported from @playwright/test.
(locator)The thing being checked. Can be a Locator, a Page, an APIResponse, or any plain value.
.toBeVisible()The matcher. It defines what condition must be true.
awaitRequired for every web-first matcher. Web-first matchers return a Promise because they retry asynchronously.
Forgetting await If you omit await on a web-first matcher, the test may pass without ever checking anything (an unawaited promise). Generic matchers like toBe are synchronous and do not take await.

Syntax variants

// 1. Web-first assertion on a locator (auto-retrying, needs await)
await expect(page.getByRole('button', { name: 'Submit' })).toBeEnabled();

// 2. Generic assertion on a plain value (synchronous, no await)
expect(items.length).toBe(3);

// 3. Negated assertion
await expect(page.getByTestId('spinner')).not.toBeVisible();

// 4. Soft assertion (does not stop the test on failure)
await expect.soft(page.getByText('Hello')).toBeVisible();

// 5. Polled assertion (retries an arbitrary async value)
await expect.poll(async () => await page.locator('.row').count()).toBeGreaterThan(5);

// 6. Custom timeout for one assertion
await expect(page.getByText('Saved')).toBeVisible({ timeout: 10_000 });

Importing

import { test, expect } from '@playwright/test';

In a JavaScript Playwright project, test and expect come from the same package. There is no separate import for assertions.

03Which expect Do I Use?

Before memorising matchers, decide which of the three families applies. This choice determines whether you get auto-retrying behaviour.

Locator / Page / APIResponse

Auto-retrying web-first assertions. Always await. Retry until timeout.

Plain JavaScript value

Synchronous generic assertions. No retry, no await. Fail immediately.

Any async value

Wrap in expect.poll() to gain retrying behaviour around a custom expression.

You have…UseRetries?Await?
A Locatorexpect(locator).toBeVisible()YesYes
A Pageexpect(page).toHaveURL(...)YesYes
An APIResponseexpect(response).toBeOK()YesYes
A string / number / arrayexpect(value).toEqual(...)NoNo
A custom async valueexpect.poll(fn).toBe(...)YesYes

05Detailed Explanation of Key Functions

Expand any function below for its full description. Use the buttons to open or close all entries.

toBeVisible()
Purpose
Asserts that the element is present in the DOM and visible to a user. Playwright retries until the element becomes visible or the timeout expires.
Syntax
await expect(locator).toBeVisible();
await expect(locator).toBeVisible({ timeout: 10_000 });
Parameters
None required. An optional options object accepts timeout (milliseconds, overrides the default).
Return / Result
Returns a Promise that resolves when the check passes and rejects with a timeout error when it does not.
Example
await page.goto('https://playwright.dev');
await expect(page.getByRole('link', { name: 'Get started' })).toBeVisible();
Expected Result
The test continues once the "Get started" link is rendered and on screen. If it never appears, the assertion fails after the timeout and the report shows the locator that was unresolved.
Common Usage
Verifying that a page loaded, a modal appeared, a validation message is shown, or a button is ready to click.
Important Notes
An element with opacity: 0 is still considered visible by Playwright, because it occupies layout space. Use toBeHidden() to assert absence, which passes for both "hidden" and "not in the DOM".
toBeHidden()
Purpose
Asserts that the element is either not attached to the DOM, or is attached but not visible.
Syntax
await expect(locator).toBeHidden();
Parameters
Optional options.timeout. A locator resolving to multiple elements is an error, so narrow it first.
Return / Result
Resolves when the element is hidden or absent; rejects on timeout otherwise.
Example
await page.getByRole('button', { name: 'Close' }).click();
await expect(page.getByTestId('loading-spinner')).toBeHidden();
Expected Result
Passes as soon as the spinner is removed or hidden after the click. This is the idiomatic way to wait for loading states to finish.
Common Usage
Waiting for spinners, toasts, modals, or error banners to disappear.
Important Notes
Because it also passes when the element does not exist, toBeHidden() is convenient but less strict than asserting the element exists and is then hidden.
toHaveText()
Purpose
Asserts that the element's text equals the expected value exactly (after whitespace normalisation). Also supports regular expressions and arrays for multiple elements.
Syntax
await expect(locator).toHaveText('Dashboard');
await expect(locator).toHaveText(/Dash\w+/);
await expect(locator).toHaveText(['One', 'Two']);
Parameters
expected — a string, RegExp, or an array of those (for locators matching several elements). Optional options.timeout.
Return / Result
Resolves when the normalised text matches. When an array is given, the number of elements must match the array length.
Example
await page.goto('https://example.com/login');
await page.getByLabel('Username').fill('demo');
await page.getByRole('button', { name: 'Sign in' }).click();
await expect(page.locator('h1')).toHaveText('Welcome, demo');
Expected Result
Passes when the heading's text is exactly "Welcome, demo". Extra surrounding whitespace is ignored; a partial match would fail.
Common Usage
Asserting headings, labels, table cells, or lists of values where the full text matters.
Important Notes
Use toContainText() for substrings. Order matters for arrays. Text is normalised (leading/trailing whitespace trimmed, internal runs collapsed).
toContainText()
Purpose
Asserts that the element's text contains the given substring, regular expression, or one of several expected values.
Syntax
await expect(locator).toContainText('error');
await expect(locator).toContainText(/error|failure/i);
await expect(locator).toContainText(['error', 'required']);
Parameters
expected — string, RegExp, or array. Optional options.timeout.
Return / Result
Resolves when any (for arrays) of the expected values is found in the element's text.
Example
await page.getByLabel('Email').fill('not-an-email');
await page.getByRole('button', { name: 'Submit' }).click();
await expect(page.getByRole('alert')).toContainText('valid email');
Expected Result
Passes if the alert text includes "valid email", e.g. "Please enter a valid email address."
Common Usage
Error messages, success banners, paragraphs, and any text where only part of the content is stable.
Important Notes
Prefer a regex or a distinctive substring over full sentences, which are brittle when copy changes.
toHaveValue()
Purpose
Asserts the current value of an <input>, <textarea>, or <select> element.
Syntax
await expect(locator).toHaveValue('demo@example.com');
await expect(locator).toHaveValue(/@example\.com$/);
Parameters
expected — string or RegExp. Optional options.timeout.
Return / Result
Resolves when the element's value matches. For a <select>, it matches the selected option value.
Example
const email = page.getByLabel('Email');
await email.fill('demo@example.com');
await expect(email).toHaveValue('demo@example.com');
Expected Result
Passes because the input's value is exactly the string that was typed in.
Common Usage
Verifying pre-filled forms, autocomplete results, clear buttons, and dropdown selections.
Important Notes
For multi-select elements use toHaveValues() with an array. Do not confuse input value with input text content.
toHaveCount()
Purpose
Asserts how many elements the locator resolves to.
Syntax
await expect(locator).toHaveCount(5);
Parameters
count — a number (integer). Optional options.timeout.
Return / Result
Resolves when the resolved element count equals the expected number; otherwise retries until timeout.
Example
await page.goto('https://demo.playwright.dev/todomvc');
await page.getByLabel('New Todo').fill('Buy milk');
await page.getByLabel('New Todo').press('Enter');
await expect(page.locator('.todo-list li')).toHaveCount(1);
Expected Result
Passes once exactly one to-do list item exists — useful for asserting that list items were added or removed.
Common Usage
Testing dynamic lists, filtering, search results, and rows added or deleted from a table.
Important Notes
Unlike most locator assertions, toHaveCount() does not require the locator to resolve to a single element.
toHaveAttribute()
Purpose
Asserts that an element has a given attribute, optionally with a specific value.
Syntax
await expect(locator).toHaveAttribute('href');
await expect(locator).toHaveAttribute('href', '/docs/intro');
await expect(locator).toHaveAttribute('aria-expanded', /true|false/);
Parameters
name (string) and optional value (string or RegExp). Optional options.timeout.
Return / Result
If only the name is given, resolves when the attribute exists. If a value is given, resolves when it matches.
Example
await page.getByRole('link', { name: 'Docs' }).click();
await expect(page.getByRole('link', { name: 'API' })).toHaveAttribute('href', '/docs/api');
Expected Result
Passes when the link's href attribute is exactly /docs/api.
Common Usage
Checking links, image src and alt, form type or disabled, and ARIA state attributes.
Important Notes
Attribute matching is case-sensitive on the value; use a RegExp with i if case varies.
toHaveClass() and toContainClass()
Purpose
toHaveClass() asserts the element's full class list; toContainClass() asserts that one specific class is present.
Syntax
await expect(locator).toHaveClass('btn btn-primary');
await expect(locator).toHaveClass(/active/);
await expect(locator).toContainClass('active');
Parameters
expected — string, RegExp, or array of class names. Optional options.timeout.
Return / Result
toHaveClass() requires the full class set to match; toContainClass() only requires the named class to be present.
Example
await page.getByRole('tab', { name: 'Settings' }).click();
await expect(page.getByRole('tab', { name: 'Settings' })).toContainClass('selected');
Expected Result
Passes when the selected tab carries the selected class, regardless of other classes on the element.
Common Usage
Asserting active/selected/disabled visual states driven by CSS classes.
Important Notes
Class order does not matter for toHaveClass(), but the set must match exactly — which is why toContainClass() or a regex is usually more robust.
toBeEnabled() and toBeDisabled()
Purpose
Assert whether a form control (or an element inheriting a disabled fieldset) is enabled or disabled.
Syntax
await expect(locator).toBeEnabled();
await expect(locator).toBeDisabled();
Parameters
Optional options.timeout.
Return / Result
Resolves when the enabled/disabled state is confirmed.
Example
const submit = page.getByRole('button', { name: 'Submit' });
await expect(submit).toBeDisabled();
await page.getByLabel('I agree').check();
await expect(submit).toBeEnabled();
Expected Result
The button starts disabled, then becomes enabled once the consent checkbox is checked.
Common Usage
Form validation flows, gated actions, and loading states that disable buttons.
Important Notes
Playwright uses the native disabled state and aria-disabled, not just a greyed-out CSS style.
toBeChecked()
Purpose
Asserts that a checkbox or radio button is checked.
Syntax
await expect(locator).toBeChecked();
await expect(locator).not.toBeChecked();
Parameters
Optional options.timeout.
Return / Result
Resolves when the checked state matches. Pair with .not to assert unchecked.
Example
const terms = page.getByRole('checkbox', { name: 'Accept terms' });
await expect(terms).not.toBeChecked();
await terms.check();
await expect(terms).toBeChecked();
Expected Result
Passes after check() sets the checkbox and the assertion observes checked.
Common Usage
Terms-of-service, filters, settings toggles, and radio groups.
Important Notes
Works with <input type="checkbox"> and "radio". For custom ARIA toggles, assert the state attribute with toHaveAttribute() instead.
toHaveURL()
Purpose
Asserts the current page URL, retrying until it matches (handy right after navigation or redirects).
Syntax
await expect(page).toHaveURL('https://example.com/dashboard');
await expect(page).toHaveURL(/\/dashboard/);
Parameters
expected — string or RegExp. Optional options.timeout. Also accepts a base URL option in some versions.
Return / Result
Resolves when page.url() matches. With a string, the comparison is a full-match after resolving relative to baseURL.
Example
await page.getByRole('button', { name: 'Log in' }).click();
await expect(page).toHaveURL(/\/dashboard$/);
Expected Result
Passes once the SPA finishes routing to a URL ending in /dashboard.
Common Usage
Login redirects, route guards, deep links, and query-string assertions.
Important Notes
Prefer a RegExp for query strings, which vary in order. This is a Page assertion — call it on page, not on a locator.
toHaveTitle()
Purpose
Asserts the document title, retrying until it matches.
Syntax
await expect(page).toHaveTitle('Playwright');
await expect(page).toHaveTitle(/Playwright/);
Parameters
expected — string or RegExp. Optional options.timeout.
Return / Result
Resolves when the title matches exactly (string) or matches the pattern (RegExp).
Example
await page.goto('https://playwright.dev');
await expect(page).toHaveTitle(/Playwright/);
Expected Result
Passes when the browser tab title contains "Playwright".
Common Usage
Smoke-testing navigation on client-rendered apps where the title is set after load.
Important Notes
The string form must match the full title; use a RegExp for partial matches.
toBeOK()
Purpose
Asserts that an API response status is in the successful 2xx range.
Syntax
await expect(response).toBeOK();
Parameters
Optional options.timeout.
Return / Result
Resolves for status codes 200–299; rejects otherwise, printing the status and status text.
Example
const response = await request.get('/api/users/1');
await expect(response).toBeOK();
Expected Result
Passes when the endpoint responds with 2xx. A 404 or 500 fails the test immediately.
Common Usage
API tests, and verifying background calls made during a UI test.
Important Notes
Only usable on an APIResponse object from the request fixture or page.waitForResponse(). It does not check the response body.
toEqual() — generic value comparison
Purpose
Performs a deep, recursive equality check on plain JavaScript values. It is a generic matcher, so it does not retry and does not take await.
Syntax
expect(actual).toEqual(expected);
Parameters
expected — any value, including asymmetric matchers such as expect.any().
Return / Result
Throws immediately if the values differ. undefined properties are ignored, unlike toStrictEqual().
Example
const response = await request.get('/api/user/1');
const body = await response.json();
expect(body).toEqual({ id: 1, name: 'Ada', role: 'admin' });
Expected Result
Passes when the parsed body is deeply equal to the expected object.
Common Usage
API payload checks, utility-function tests, and any non-UI value comparison.
Important Notes
Do not await it. If you need retrying on a value that changes over time, wrap the source in expect.poll().
expect.poll()
Purpose
Retries an arbitrary async (or sync) function until the following matcher passes, giving non-locator values the same auto-retrying behaviour as web-first assertions.
Syntax
await expect.poll(async () => expression, options).toBe(expected);
Parameters
The function to poll; options.timeout (default 5s), options.intervals (array of retry delays in ms), and options.message.
Return / Result
Awaits the promise chain: it calls the function repeatedly and applies the matcher until it passes or the timeout expires.
Example
await expect.poll(async () => {
  const response = await page.request.get('/api/status');
  return (await response.json()).state;
}, { timeout: 10_000 }).toBe('ready');
Expected Result
Polls the endpoint until state becomes 'ready', or fails after 10 seconds.
Common Usage
Asserting DB or backend state that updates asynchronously after a UI action, or counting DOM nodes.
Important Notes
Keep the polled function side-effect-free and fast. Any thrown error inside it is treated as a retry, not an immediate failure, unless you rethrow deliberately.
expect.soft()
Purpose
Runs an assertion without aborting the test on failure. The test is marked failed, but execution continues so remaining assertions still run.
Syntax
await expect.soft(locator).toBeVisible();
expect.soft(value).toBe(3);
Parameters
The same value/locator as expect, followed by any matcher. Web-first usage still needs await.
Return / Result
Never throws mid-test; failures are collected and reported at the end of the test. Use test.info().errors to inspect them.
Example
test('dashboard widgets', async ({ page }) => {
  await page.goto('/dashboard');
  await expect.soft(page.getByTestId('sales')).toBeVisible();
  await expect.soft(page.getByTestId('orders')).toBeVisible();
  await expect.soft(page.getByTestId('users')).toBeVisible();
});
Expected Result
All three widgets are checked even if the first is missing, and the report lists every widget that failed.
Common Usage
Verifying many independent UI elements in one pass, or running a "health check" test that should report all issues.
Important Notes
Do not use soft assertions for preconditions — if a later step depends on the value, a hard assertion gives a clearer failure.
.not modifier
Purpose
Inverts any matcher: the assertion passes when the normal matcher would fail.
Syntax
await expect(locator).not.toBeVisible();
expect(value).not.toEqual(0);
Parameters
None — it is a property that returns the negated assertion object.
Return / Result
Behaves exactly like the underlying matcher but with the opposite expectation.
Example
await page.getByRole('button', { name: 'Delete' }).click();
await expect(page.getByText('Are you sure?')).not.toBeVisible();
Expected Result
Passes once the confirmation dialog's text is gone from the screen.
Common Usage
Asserting absence, unchanged state, or that an action had no effect.
Important Notes
Negated web-first assertions still retry, so they wait for the condition to become false. Avoid double negatives that are hard to read.
toHaveScreenshot()
Purpose
Compares the current rendering of a page or element against a stored baseline image, catching unintended visual changes.
Syntax
await expect(page).toHaveScreenshot();
await expect(locator).toHaveScreenshot('card.png', { maxDiffPixels: 50 });
Parameters
Optional name; options include maxDiffPixels, maxDiffPixelRatio, threshold, animations, and mask.
Return / Result
Resolves when the image matches within tolerance. On failure it writes actual/expected/diff images to the test output folder.
Example
await page.goto('/pricing');

06Practical Examples

Example 1 — Basic Usage

The simplest possible assertion: open a page and confirm a heading is visible.

import { test, expect } from '@playwright/test';

test('home page shows a heading', async ({ page }) => {
  await page.goto('https://example.com');
  await expect(page.getByRole('heading', { level: 1 })).toBeVisible();
});

Example 2 — Real-World Usage

A login flow that verifies the redirect URL, a welcome message, and that the login form is gone.

import { test, expect } from '@playwright/test';

test('user can log in', async ({ page }) => {
  await page.goto('https://demo.example.com/login');

  await page.getByLabel('Email').fill('qa@example.com');
  await page.getByLabel('Password').fill('secret123');
  await page.getByRole('button', { name: 'Log in' }).click();

  await expect(page).toHaveURL(/\/dashboard/);
  await expect(page.getByRole('heading', { name: 'Welcome back' })).toBeVisible();
  await expect(page.getByLabel('Password')).toBeHidden();
});

Example 3 — Multiple Functions

Combining locator assertions, value assertions, counting, and generic matchers in one test.

import { test, expect } from '@playwright/test';

test('to-do list behaves correctly', async ({ page }) => {
  await page.goto('https://demo.playwright.dev/todomvc');
  const input = page.getByPlaceholder('What needs to be done?');
  const items = page.locator('.todo-list li');

  await input.fill('Buy milk');
  await input.press('Enter');
  await input.fill('Walk the dog');
  await input.press('Enter');

  await expect(items).toHaveCount(2);
  await expect(items.first()).toHaveText('Buy milk');
  await expect(items.nth(1)).toContainText('dog');

  await expect(input).toBeEmpty();
  await expect(page).toHaveTitle(/TodoMVC/);
  expect(await items.count()).toBeGreaterThan(0);
});

Example 4 — Negative Scenario

An assertion that is expected to fail, with an explanation of why.

import { test, expect } from '@playwright/test';

test('this assertion fails on purpose', async ({ page }) => {
  await page.goto('https://example.com');

  // The button does not exist on this page, so this assertion will time out.
  await expect(page.getByRole('button', { name: 'Buy now' })).toBeVisible();
});

Why it fails: the locator resolves to zero elements, so the matcher retries until the 5-second timeout and then fails with "Locator: getByRole('button', { name: 'Buy now' }) ... waiting for element to be visible". To assert the opposite, use .not.toBeVisible().

Example 5 — Advanced Usage

API verification, polled backend state, and soft assertions in a single test.

import { test, expect } from '@playwright/test';

test('order is processed end to end', async ({ page, request }) => {
  // API-level assertion
  const health = await request.get('/api/health');
  await expect(health).toBeOK();
  const healthBody = await health.json();
  expect(healthBody).toMatchObject({ status: 'up' });

  // UI action that triggers background processing
  await page.goto('/orders/new');
  await page.getByRole('button', { name: 'Place order' }).click();

  // Poll the backend until the order is confirmed
  await expect.poll(async () => {
    const res = await request.get('/api/orders/latest');
    return (await res.json()).status;
  }, { timeout: 15_000, intervals: [500, 1000, 2000] }).toBe('confirmed');

  // Soft assertions collect all failures before reporting
  await expect.soft(page.getByTestId('order-id')).toBeVisible();
  await expect.soft(page.getByText('Thank you')).toBeVisible();

  // Custom, reusable expect with a longer timeout
  const slow = expect.configure({ timeout: 10_000 });
  await slow(page.getByTestId('receipt')).toBeVisible();
});

07Before vs After

Playwright's assertions replace manual waiting patterns. This comparison is meaningful because the "before" version is a real, common approach in older tools.

Without web-first assertions (manual polling)

// Traditional approach: wait, read, compare, repeat by hand
import { test, expect } from '@playwright/test';

test('message appears', async ({ page }) => {
  await page.goto('/inbox');
  await page.waitForTimeout(3000);            // guess how long to wait

  const text = await page.locator('.status').textContent();
  expect(text).toBe('Sent');                  // no retry: flaky if too early
});

With web-first assertions

// Playwright approach: declare the condition, let the framework retry
import { test, expect } from '@playwright/test';

test('message appears', async ({ page }) => {
  await page.goto('/inbox');
  await expect(page.locator('.status')).toHaveText('Sent'); // retries automatically
});

Why the "after" version is better

  • No fixed sleeps — the assertion returns as soon as the condition holds, so fast runs stay fast.
  • No flakiness — slow environments simply retry until the timeout instead of failing.
  • Better failures — the error shows the expected value and the actual element state, not just "undefined !== 'Sent'".
  • Less code — one line replaces a wait plus a read plus a compare.

09Best Practices

  1. Always await web-first assertions. It is the most common cause of tests that pass without checking anything.
  2. Assert on the locator, not a resolved value. await expect(locator).toHaveText(...) retries; reading textContent() first does not.
  3. Use user-facing locators. Prefer getByRole, getByLabel, and getByText in assertions — they are resilient to DOM refactors and read like the user's intent.
  4. Never use waitForTimeout() before an assertion. Let the auto-retry mechanism do the waiting.
  5. Keep assertions specific. A locator matching one element produces clear failures; a broad locator produces "strict mode violation" noise.
  6. Assert the outcome, not the implementation. Check that the success banner shows, not that a particular CSS class was toggled, unless the class truly is the contract.
  7. Prefer toContainText() over toHaveText() for human-readable copy that may change slightly.
  8. Use expect.soft() for independent checks so one missing widget does not hide the others.
  9. Group related assertions near the action they verify, so a failure points directly at the step that broke.
  10. Centralise timeouts. Configure a project-wide expect: { timeout } and override only for known-slow cases.
  11. Use expect.poll() for backend state, not for DOM state — the DOM already has web-first matchers.
  12. Keep visual assertions deterministic. Mask dynamic content and run screenshot tests in a consistent CI image.

10Interview Questions

Beginner Questions

1. What is expect in Playwright and where does it come from?
It is the assertion library exported by @playwright/test. It combines generic value matchers with Playwright's auto-retrying web-first matchers. It is imported alongside test from the same package.
2. Why do web-first assertions need await?
Because they retry asynchronously and return a Promise. Without await, the test does not wait for the result and the assertion may never be evaluated.
3. What is the difference between toHaveText() and toContainText()?
toHaveText() requires the full, normalised text to match; toContainText() passes when the text contains the given substring or matches the given pattern.
4. How do you assert that an element is not visible?
Use the .not modifier: await expect(locator).not.toBeVisible(). Note it passes if the element is hidden or absent.
5. What does toBeChecked() verify?
That a checkbox or radio button is in the checked state. Use .not.toBeChecked() for the unchecked case.

Intermediate Questions

1. Why is await expect(locator).toHaveText('x') safer than expect(await locator.textContent()).toBe('x')?
The first auto-retries until the text matches or times out. The second reads the value once, so it fails immediately if the UI has not updated yet — a classic source of flakiness.
2. When would you use expect.poll()?
When the value you need to assert is not a locator property — for example, backend state fetched over HTTP, a database record, or a computed counter that updates asynchronously.
3. What does expect.soft() do and when is it useful?
It records a failure without aborting the test, so all soft assertions run. It is useful when verifying several independent elements and you want a complete list of failures.
4. How does Playwright decide whether an element is "visible"?
An element is visible when it is attached and has a non-empty bounding box and is not hidden by display:none, visibility:hidden, or zero opacity is not excluded — note that opacity:0 still counts as visible because the element occupies space.
5. Why might await expect(page.locator('button')).toBeVisible() fail even though a button is on the page?
Because the locator matches more than one element, which is a strict-mode violation. Narrow the locator to a single, uniquely identified element.

Advanced Questions

1. How would you give one assertion a longer timeout without changing global settings?
Pass an options object: await expect(locator).toBeVisible({ timeout: 10_000 }). For a set of assertions, create a configured expect: const slow = expect.configure({ timeout: 10_000 }).
2. What is the difference between toEqual() and toStrictEqual()?
toEqual() ignores properties whose value is undefined and does not check the prototype; toStrictEqual() also verifies the type/prototype and treats undefined properties as significant.
3. How do custom matchers get registered in Playwright?
With expect.extend({ ... }), providing an object whose keys are matcher names returning { pass, message }. They then work on any expect call, including .not.
4. A web-first assertion is polling for 30 seconds and then failing. How do you diagnose it?
Inspect the trace/report to see the locator Playwright tried and the element state it observed. Common causes: a broad locator (strict-mode violation), the element is inside an iframe or shadow root not reached by the locator, or the app is genuinely slower than the timeout.
5. How can a flaky visual assertion be made reliable?
Mask dynamic regions, disable animations, set a small maxDiffPixelRatio, and run the tests in a container image that pins the OS, fonts, and browser version so rendering is reproducible.

13Key Takeaways

  • expect comes from @playwright/test and mixes auto-retrying web-first matchers with synchronous generic matchers.
  • Web-first assertions (locator, page, APIResponse) need await; generic value matchers do not.
  • Assert on the locator, not on a resolved value — that is what gives you retrying and readable failures.
  • Use .not to negate, expect.soft() to keep going after a failure, and expect.poll() to retry non-locator values.
  • Prefer user-facing locators (getByRole, getByLabel) and specific text matchers to keep assertions stable.
  • Never use waitForTimeout() as a substitute for an assertion’s built-in retry.
  • Centralise timeouts in configuration and override per assertion only when genuinely needed.
  • Good assertions verify user-visible outcomes, not implementation details.
