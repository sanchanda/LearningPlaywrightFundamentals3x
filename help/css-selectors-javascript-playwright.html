Selector Reference

CSS Selectors in JavaScript / Playwright

Patterns that match DOM elements by tag, class, id, attribute, and structural position — the default selector engine in Playwright, extended with its own pseudo-classes.

@playwright/test Default engine locator('.class') Beginner → Advanced

01What Is It?

CSS selectors are patterns that match elements in a DOM tree. They are the language you already use in stylesheets, and they are also the default selector engine in Playwright — when you write page.locator('.btn'), you are using CSS.

A selector answers the question "which element(s)?" by describing what the element is or where it sits:

form.checkout input[type="email"]

That reads as: an input whose type is email, inside any element with class checkout on a form.

Why it exists

CSS selectors were designed for styling, so they are concise, fast, and supported natively by the browser through querySelector / querySelectorAll. Because the whole web already speaks CSS, using it for testing means no new syntax for developers to learn.

What problem it solves

  • Precise, compact targeting — #login is shorter and faster than a full XPath.
  • Attribute matching — match by any attribute, with prefix, suffix, and substring operators.
  • Structural matching — target the first row, the last item, or every third card.
  • Composability — Playwright adds :has(), :has-text(), and :nth-match() on top of standard CSS.

Where it is commonly used

  • Playwright locators — the default, and the engine behind getByTestId (which targets a data attribute).
  • Browser DevTools styles and the elements panel.
  • Selenium, Cypress, Puppeteer, and virtually every browser automation tool.
  • JavaScript DOM queries in application code.

When a tester should use it

CSS is a strong default for attribute and structure matching: test ids, names, types, and roles expressed as attributes. Prefer Playwright's user-facing locators where they fit, use CSS when the element is best identified by an attribute or a structural relationship, and reach for XPath only when you need text matching or upward traversal.

CSS only matches downward CSS has no parent or ancestor selector. You can match a child, a descendant, or a following sibling, but you cannot select "the parent of this cell" in plain CSS. Playwright's :has() helps by matching a container that contains something, and its filter() API lets you narrow a set — but for true upward traversal you need XPath.

02Syntax

Basic form

tag.class[attribute="value"]:pseudo-class

Broken down for button.btn-primary[type="submit"]:enabled:

PartMeaning
buttonType selector — matches elements with that tag name.
.btn-primaryClass selector — element has that class in its class list.
[type="submit"]Attribute selector — attribute exists and equals the value.
:enabledPseudo-class — state or structural condition (here, not disabled).

All parts of a compound selector apply to the same element. Adding a space or a combinator moves to a different element.

Space matters div.card means "a div that has class card". div .card (with a space) means "an element with class card inside a div". These match different elements.

Selector variants

#login                       // id="login"
.btn                         // class contains "btn"
[data-testid="submit"]       // attribute equals
[href^="https://"]           // attribute starts with
[href$=".pdf"]               // attribute ends with
[class*="card"]              // attribute contains substring
ul > li                      // direct child
h2 + p                       // immediately following sibling
h2 ~ p                       // any following sibling
li:first-child               // first child of its parent
li:nth-child(2n+1)           // odd children
input:not([disabled])        // negation
article:has(img)             // contains a descendant img (Playwright)
:is(h1, h2, h3)              // any of these

Playwright usage

// CSS is the default engine
const button = page.locator('button.btn-primary');

// Explicit prefix when you want to be unambiguous
const input = page.locator('css=input[type="email"]');

// Chained: CSS scoped to the result of the previous locator
const price = page.locator('.product-card').locator('.price');

// Narrow a set with filter()
const inStock = page.locator('.product-card').filter({ hasText: 'In stock' });

03CSS in Playwright

Playwright implements the full CSS selector syntax plus additional pseudo-classes of its own. A CSS locator behaves like any other locator: it auto-waits, respects strict mode, chains, and works with expect.

Key facts

  • It is the default. No prefix is needed — page.locator('.card') uses the CSS engine. Add css= only to remove ambiguity.
  • Strict mode applies. A selector matching multiple elements throws on action; narrow it or use .first() / .nth().
  • Auto-waiting applies. The locator waits for the element to be actionable — no manual waits.
  • It pierces open shadow DOM. Unlike XPath, Playwright's CSS engine crosses open shadow roots. The :light() extension restricts a match to the light DOM.
  • It is fast. The engine compiles the selector and runs it against the DOM natively.
  • It only matches downward. No parent/ancestor axis — use :has(), filter(), or XPath.
Prefer user-facing locators first Playwright recommends getByRole, getByLabel, getByPlaceholder, getByText, and getByTestId. Use raw CSS when an attribute or structural relationship is the clearest identifier, and avoid long chains of classes that change with styling.

The three families of Playwright locators

User-facing (best)

getByRole('button', { name: 'Save' }) — accessible, stable, readable.

CSS / test id (good)

locator('[data-testid="save"]') or locator('.card .title') — fast and precise.

XPath (fallback)

locator('xpath=//td[text()="Ada"]/..') — for text and upward traversal.

Using CSS with assertions

await expect(page.locator('h1.title')).toHaveText('Dashboard');
await expect(page.locator('.todo-list li')).toHaveCount(3);
await expect(page.locator('button[type="submit"]')).toBeEnabled();
await expect(page.locator('.card').filter({ hasText: 'Laptop' })).toBeVisible();

Playwright adds pseudo-classes that are not part of the CSS standard. They are only valid inside a Playwright locator.

:visible is legacy Playwright still supports the :visible pseudo-class, but the modern way to filter to visible elements is locator.filter({ visible: true }), which composes with other filters and reads more clearly. For assertions, expect(locator).toBeVisible() is the idiomatic choice.
Prefer filter() over pseudo-class soup Playwright's locator.filter({ has, hasText, hasNot }) expresses the same ideas as :has() and :has-text() but yields a reusable, chainable locator with clearer failure messages.

Text matching notes

  • Matching is case-insensitive and whitespace-normalised for :has-text() and :text().
  • :text() matches the smallest element containing the text, then falls back to the smallest element that contains it as a substring.
  • :text-is() requires the full text to match exactly.
  • For input elements of type button and submit, the value attribute is matched instead of text content.

06Detailed Explanation of Key Selectors

Expand any selector for its full description. Use the buttons to open or close all entries.

[attr], [attr="v"], ^=, $=, *= — attribute selectors
Purpose
Match elements by the presence or content of an HTML attribute, without relying on classes that change with styling.
Syntax
[disabled]            /* attribute exists        */
[type="email"]        /* exactly equals          */
[href^="https://"]    /* starts with             */
[href$=".pdf"]        /* ends with               */
[class*="card"]       /* contains substring      */
[class~="card"]       /* contains the whole word */
[type="EMAIL" i]      /* case-insensitive exact  */
Parameters
The attribute name, optionally followed by an operator and a quoted value. The trailing i flag makes the comparison case-insensitive.
Return / Result
A node set of every element satisfying the condition.
Example
await page.locator('input[type="email"]').fill('qa@example.com');
await page.locator('a[href$=".pdf"]').first().click();
await page.locator('[data-testid="submit"]').click();
Expected Result
Each locator resolves to the matching element(s); assertions and actions behave normally.
Common Usage
Targeting form fields, links by destination, and elements carrying data-* test attributes.
Important Notes
[class*="card"] is a raw substring test, so it also matches card-header. Use [class~="card"] to match the whole class token. For ids that are not valid identifiers (for example #123), use an attribute selector: [id="123"].
Combinators: descendant, >, +, ~
Purpose
Express the positional relationship between two elements: inside, direct child, immediate sibling, or any later sibling.
Syntax
A B     /* B anywhere inside A        */
A > B   /* B is a direct child of A   */
A + B   /* B is the next sibling of A */
A ~ B   /* B is any later sibling of A*/
Parameters
Two selectors joined by a combinator. Either side may be a complex compound selector.
Return / Result
The set of elements matching the right-hand selector in that relationship to a left-hand match.
Example
await page.locator('nav > ul > li').first().click();
await page.locator('form input[type="text"]').fill('Ada');
await page.locator('label + input').fill('Ada');
Expected Result
Only the elements in the specified relationship are matched — direct children for >, siblings for + and ~.
Common Usage
Scoping a search under a container, and pairing a label with its input via the sibling combinator.
Important Notes
Sibling combinators only look forward in the document; there is no previous-sibling combinator. Keep chains short — a four-level descendant chain is brittle.
:nth-child() and :nth-of-type()
Purpose
Select elements by their position among siblings, using a number, a keyword, or an an+b formula.
Syntax
li:nth-child(2)      /* the 2nd child        */
li:nth-child(odd)    /* 1st, 3rd, 5th ...    */
li:nth-child(2n)     /* even children        */
li:nth-child(3n+1)   /* 1st, 4th, 7th ...    */
p:nth-of-type(2)     /* the 2nd <p> sibling */
Parameters
An integer, odd / even, or an an+b expression. :nth-of-type() counts only siblings of the same tag.
Return / Result
The elements occupying those positions within their parent.
Example
await expect(page.locator('table tbody tr:nth-child(2)')).toContainText('Ada');
await page.locator('ul > li:nth-child(odd)').first().click();
Expected Result
Matches the specified rows/items based on their index among siblings.
Common Usage
Fixed tables and grids where an element has no unique attribute, such as asserting the second row of a result set.
Important Notes
:nth-child() counts every sibling regardless of tag, while :nth-of-type() counts only elements of the same tag. Positions shift when rows are inserted, so prefer a unique attribute or getByRole with a name when possible.
:has() — container that contains a descendant
Purpose
Matches an element only if it contains a descendant matching the inner selector. It is the closest CSS gets to "select a parent", and Playwright supports it in locators.
Syntax
outer:has(inner)
outer:has(> inner)   /* direct child only */
Parameters
A selector describing the required descendant, optionally with a > to require a direct child.
Return / Result
The set of outer elements that contain at least one matching descendant.
Example
await page.locator('.product-card:has(.badge.out-of-stock)')
  .locator('button.add-to-cart')
  .first()
  .click();
Expected Result
Finds a product card that contains an out-of-stock badge, then clicks its add-to-cart button.
Common Usage
Row-scoped actions, selecting cards by their contents, and asserting state on a container.
Important Notes
Playwright also exposes this as locator.filter({ has: locator }), which is preferred when the inner condition is a locator and gives clearer errors. :has() cannot look upwards, only at descendants.
:has-text() — match by contained text
Purpose
Filters elements to those whose text content contains the given string, case-insensitively and with whitespace normalised.
Syntax
selector:has-text("text")
Parameters
A text string, optionally quoted. Matching is a substring test against the element's text content.
Return / Result
Elements containing the text anywhere within them.
Example
await page.locator('button:has-text("Sign in")').click();
await expect(page.locator('.alert:has-text("Invalid credentials")')).toBeVisible();
Expected Result
Matches the button whose label contains "Sign in" and the alert containing the error text.
Common Usage
Quick text-based targeting combined with a structural or attribute selector for precision.
Important Notes
It matches the element and its ancestors, so an overly broad base selector can match several nodes — combine with a tag or class. Use getByText() or filter({ hasText }) for a more semantic, better-named alternative.
:text-is() and :text()
Purpose
:text-is() matches text exactly, while :text() performs a smart match, preferring the element whose own text equals the value and falling back to the smallest element containing it.
Syntax
:text-is("Submit")
:text("Submit")
Parameters
A text string. Matching is case-insensitive and whitespace-normalised in both forms.
Return / Result
The matching element(s). :text-is() rejects partial matches; :text() accepts them.
Example
await page.locator(':text-is("Submit")').click();
await expect(page.locator(':text("Order #")')).toBeVisible();
Expected Result
The first locator matches only the element whose full text is "Submit"; the second matches an element containing the phrase.
Common Usage
Differentiating "Save" from "Save draft", or targeting a label that includes dynamic values.
Important Notes
These are Playwright text-engine concepts used inside CSS; for everyday tests getByText() with { exact: true } is the recommended, more readable form.
:nth-match()
Purpose
Selects the nth element matching a selector across the whole document, which avoids the per-parent behaviour of :nth-child().
Syntax
:nth-match(selector, index)
Parameters
A selector and a 1-based index.
Return / Result
A single element — the nth match of the selector in document order.
Example
await page.locator(':nth-match(button.btn, 3)').click();
Expected Result
Clicks the third button with class btn in the document, regardless of which parent it lives in.
Common Usage
Picking one element from a set that spans multiple containers, where per-parent indexing would be wrong.
Important Notes
Often locator('button.btn').nth(2) is preferable — it is clearer and avoids the legacy pseudo-class syntax. Both are 1-based via :nth-match and 0-based via .nth(); mind the difference.
:not(), :is(), :where()
Purpose
Logical negation and grouping inside a selector. :not() excludes; :is() and :where() accept any of several alternatives.
Syntax
input:not([disabled])
:is(h1, h2, h3)
:where(.a, .b)
Parameters
One or more selectors. :where() behaves like :is() but contributes zero specificity (relevant in stylesheets, not in tests).
Return / Result
Elements that fail the negated selector, or that match any listed alternative.
Example
await page.locator('button:not([disabled])').first().click();
await expect(page.locator(':is(h1, h2):has-text("Dashboard")')).toBeVisible();
Expected Result
Targets the first enabled button, and the heading among h1/h2 containing "Dashboard".
Common Usage
Excluding hidden or disabled options, and grouping headings or list roles.
Important Notes
:not() takes a selector list in modern browsers, but keep it simple for portability. Negation complements the CSS inability to traverse upward — it filters a set rather than finding a parent.
:visible and filter({ visible: true })
Purpose
Narrow a set to elements that are actually visible, which is common when a hidden template copy and a rendered copy share the same markup.
Syntax
page.locator('li:visible')                              /* legacy pseudo-class */
page.locator('li').filter({ visible: true })            /* modern API        */
Parameters
The pseudo-class takes no arguments; filter() accepts an options object with visible.
Return / Result
Only elements that are visible (non-empty bounding box, not hidden by CSS).
Example
const visibleCount = page.locator('.todo-list li').filter({ visible: true });
await expect(visibleCount).toHaveCount(2);
Expected Result
Counts only the list items that are actually rendered, ignoring hidden ones.
Common Usage
Menus with duplicated mobile/desktop markup, tabs where inactive panels remain in the DOM.
Important Notes
Prefer filter({ visible: true }) over the :visible pseudo-class. When you simply want to assert visibility, use expect(locator).toBeVisible().

07Practical Examples

Example 1 — Basic Usage

Locate an element by id and class, then assert it is visible.

import { test, expect } from '@playwright/test';

test('click the login button', async ({ page }) => {
  await page.goto('https://example.com');

  const login = page.locator('button#login.btn-primary');
  await expect(login).toBeVisible();
  await login.click();
});

Example 2 — Real-World Usage

A login form using attribute, child, and sibling selectors.

import { test, expect } from '@playwright/test';

test('user can log in', async ({ page }) => {
  await page.goto('https://demo.example.com/login');

  await page.locator('form.login input[type="email"]').fill('qa@example.com');
  await page.locator('form.login input[type="password"]').fill('secret123');
  await page.locator('form.login button[type="submit"]').click();

  await expect(page).toHaveURL(/\/dashboard/);
  await expect(page.locator('header .user-name')).toHaveText('QA User');
});

Example 3 — Multiple Selectors

Combining :has(), :has-text(), structural pseudo-classes, and attribute selectors.

import { test, expect } from '@playwright/test';

test('filter and act on product cards', async ({ page }) => {
  await page.goto('/catalogue');

  // Cards that contain an out-of-stock badge
  await expect(page.locator('.card:has(.badge.out-of-stock)')).toHaveCount(2);

  // The first in-stock card's add button
  await page.locator('.card:has-text("In stock"):nth-child(1) button.add')
    .click();

  // Attribute + child combinator
  await expect(page.locator('table#cart > tbody > tr')).toHaveCount(1);

  // Sibling combinator: the error paragraph after the email field
  await expect(page.locator('input[type="email"] + p.error')).toBeHidden();
});

Example 4 — Negative Scenario

A selector that matches nothing, and why.

import { test, expect } from '@playwright/test';

test('this selector fails on purpose', async ({ page }) => {
  await page.goto('https://example.com');

  // There is no element with data-testid="buy-now" on this page
  await page.locator('[data-testid="buy-now"]').click();
});

Why it fails: the attribute selector matches zero elements, so the action times out waiting for the element to appear and become actionable. If a strict-mode error appears instead, the selector matched several elements and needs narrowing.

Example 5 — Advanced Usage

Scoped chains, filtering with has and hasText, structural selection, and a polled assertion.

import { test, expect } from '@playwright/test';

test('advanced CSS techniques', async ({ page }) => {
  await page.goto('/orders');

  // Scope a search to a specific panel
  const panel = page.locator('section#open-orders');
  await expect(panel.locator('table tbody > tr')).toHaveCount(3);

  // filter({ has }) == :has(), filter({ hasText }) == :has-text()
  const appleRow = panel.locator('tbody > tr').filter({
    has: page.locator('td.customer', { hasText: 'Apple' }),
  });
  await expect(appleRow).toHaveCount(1);

  // Structural pseudo-classes
  const firstRow = panel.locator('tbody > tr:nth-child(1)');
  await expect(firstRow.locator('td.status')).toHaveText('Open');

  // Sibling combinator for the summary after the table
  await expect(panel.locator('table + .summary')).toBeVisible();

  // Poll a computed value
  await expect.poll(async () => await panel.locator('tbody > tr').count()).toBe(3);
});

08Before vs After

Playwright replaced the old page.$ / waitForSelector pattern with locators. This is a real migration for CSS-based suites.

Without locators (element handles + manual waits)

// Old approach: handle resolved once, no auto-waiting, no retrying assertions
import { test, expect } from '@playwright/test';

test('old style', async ({ page }) => {
  await page.goto('/inbox');

  await page.waitForSelector('.compose-btn', { state: 'visible' });
  const handle = await page.$('.compose-btn');
  await handle.click();

  const status = await page.$('.status');
  expect(await status.textContent()).toBe('Ready');   // no retry: flaky
});

With CSS locators (current API)

// Modern approach: auto-waiting locator + retrying assertion
import { test, expect } from '@playwright/test';

test('new style', async ({ page }) => {
  await page.goto('/inbox');

  await page.locator('.compose-btn').click();
  await expect(page.locator('.status')).toHaveText('Ready');
});

Why the "after" version is better

  • Auto-waiting — the locator waits for actionability; the handle had to be found first and could go stale.
  • Retrying assertions — toHaveText() retries; reading textContent() once does not.
  • Strict mode — ambiguous selectors fail loudly instead of silently using the first match.
  • Composability — chaining, filter(), and .nth() build precise locators from simple ones.

09Common Mistakes

MistakeWhy It HappensIncorrect ExampleCorrect Example
Selecting on generated class names CSS-in-JS produces hashed classes that change each build. locator('.css-1x2y3z') locator('[data-testid="submit"]')
Over-long descendant chains Copied from DevTools; any markup change breaks it. locator('div > div > main > form > div > input') locator('form input[type="email"]')
Confusing descendant with child Forgetting that a space matches any depth. locator('ul li') for direct items only locator('ul > li')
Substring class matching *= is a raw substring, not a token match. [class*="card"] also matches card-header [class~="card"]
Using an invalid id selector Ids that start with a digit or need escaping. locator('#123') locator('[id="123"]')
Mixing up :nth-child and :nth-of-type One counts all siblings, the other only same-tag siblings. p:nth-child(2) when a heading precedes it p:nth-of-type(2)
Ignoring strict mode A broad selector matches several elements and errors. locator('.btn').click() locator('.card:has-text("Laptop") .btn').click()
Broad :has-text() base Text matches ancestors too, so many nodes qualify. locator(':has-text("Save")') locator('button:has-text("Save")')
Relying on :hover or ::before Generated and transient states are not matchable DOM. locator('.tooltip::after') hover() the trigger, then assert the real tooltip element

10Best Practices

  1. Prefer user-facing locators first. Use getByRole / getByLabel / getByTestId before raw CSS.
  2. Anchor on stable attributes. [data-testid], [name], and [type] change far less than classes or structure.
  3. Avoid generated class names. Hashed CSS-in-JS classes are build artifacts, not contracts.
  4. Keep selectors short. One or two steps; a long descendant chain is a maintenance liability.
  5. Use the child combinator when you mean direct. A space matches any depth and can pull in nested elements.
  6. Prefer [class~="token"] over [class*="token"] to avoid substring collisions like card matching card-header.
  7. Use filter() over :has() / :has-text() in modern code — it chains better and produces clearer failures.
  8. Respect strict mode. Aim for exactly one match rather than hiding ambiguity with .first().
  9. Scope before you search. Locate a container once, then chain — it is faster and prevents cross-page matches.
  10. Avoid positional selectors for uniqueness. :nth-child() shifts when data changes; use it only for genuinely positional assertions.
  11. Do not target pseudo-elements. ::before / ::after content is not in the DOM.
  12. Encapsulate fragile selectors. Keep them inside page objects so a markup change is a one-line fix.

11Interview Questions

Beginner Questions

1. Are CSS selectors the default in Playwright?
Yes. page.locator('.btn') uses the CSS engine. Other engines are selected with a prefix such as xpath= or the getBy* methods.
2. What is the difference between .btn and #btn?
.btn matches elements whose class list contains btn; #btn matches the single element whose id is btn.
3. What does ul > li match compared with ul li?
ul > li matches only li that are direct children of a ul; ul li matches li at any depth below a ul.
4. How do you select an input by its type?
With an attribute selector: input[type="email"], or [type="email"] to allow any tag.
5. What does :nth-child(2) select?
The element that is the second child of its parent, counting all sibling elements regardless of tag. :nth-of-type(2) counts only siblings of the same tag.

Intermediate Questions

1. Can CSS select a parent element? How do you work around it?
No — CSS only matches downward. Use Playwright's :has() or filter({ has }) to match a container by its descendant, or switch to XPath (/..) for true upward traversal.
2. What is the difference between [class*="card"] and [class~="card"]?
*= is a raw substring test, so it also matches card-header. ~= matches only when card appears as a whitespace-separated word, i.e. a whole class token.
3. How does Playwright's strict mode affect CSS locators?
If a selector resolves to more than one element, actions and assertions throw a strict-mode violation. Narrow the selector or resolve it with .first() / .nth().
4. What does :has-text() do, and why can it be too broad?
It filters elements whose text content contains the string, case-insensitively. Because ancestors also contain that text, an unqualified base selector matches many nodes — always anchor it to a tag or class.
5. Why is .css-1x2y3z a bad locator?
It is a generated hash from a CSS-in-JS tool. It carries no semantic meaning and changes between builds, so the test breaks whenever styles are regenerated. Use a test id or a stable attribute instead.

Advanced Questions

1. How does Playwright's CSS engine differ from querySelectorAll?
Playwright's engine is a superset: it adds pseudo-classes such as :has(), :has-text(), :nth-match(), and :visible, and it can pierce open shadow DOM. Plain querySelectorAll supports only standard CSS and does not cross shadow boundaries.
2. When would you choose XPath over CSS?
When you need upward traversal (parent/ancestor), sibling selection that runs backwards, or text matching that CSS cannot express. For attribute and structural matching, and for shadow DOM, CSS is preferable.
3. How would you locate the row containing "Ada" and click its Edit button in CSS?
Match the row by its content, then chain: page.locator('tr:has(td:has-text("Ada"))').locator('button:has-text("Edit")'). In modern code, .filter({ hasText: 'Ada' }) reads better.
4. Why can you not assert on ::before content with a selector?
Pseudo-elements are generated by CSS and are not in the DOM node tree, so no selector engine can address them. Assert the parent element's rendered text or use a visual assertion instead.
5. A selector works in DevTools but fails in Playwright. What could differ?
Playwright's strict mode may be reporting a multi-match, shadow DOM may be involved, the element may be inside an iframe (which needs frameLocator), or the element may not yet exist. Check the locator in the trace viewer for the exact state Playwright observed.

14Key Takeaways

  • CSS is the default selector engine in Playwright — no prefix is required for locator('.class').
  • Playwright extends standard CSS with :has(), :has-text(), :text-is(), :nth-match(), :visible, and :light().
  • CSS matches downward only; there is no parent selector. Use :has(), filter(), or XPath for containers and upward traversal.
  • Attribute selectors ([data-testid], [name], [type]) are more stable than class names, and far more stable than generated hashes.
  • [class*=...] is a substring test; [class~=...] matches a whole class token.
  • Prefer locator.filter() and the getBy* locators over pseudo-class-heavy selectors — they read better and fail more clearly.
  • Strict mode, auto-waiting, chaining, and shadow-DOM piercing all apply to CSS locators.
  • Pseudo-elements are not in the DOM and cannot be targeted by any selector.
