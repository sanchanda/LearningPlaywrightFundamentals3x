XPath in JavaScript / Playwright

XML Path Language expressions used to locate elements in the DOM — how to write them, when to use them, and how Playwright evaluates them.

@playwright/test XPath 1.0 locator('xpath=...') Beginner → Advanced

01What Is It?

XPath (XML Path Language) is a W3C query language for selecting nodes from an XML or HTML document. In a browser it runs over the parsed DOM through the native document.evaluate() API, and in Playwright you use it through locator('xpath=...').

XPath treats a document as a tree of nodes. You write a path through that tree — much like a file system path — optionally filtered by predicates and functions:

//div[@class="card"]//a[contains(@href, "/product/")]

Why it exists

XPath predates CSS selectors and was designed for XML documents, where CSS had no equivalent. It remains valuable in testing because it can do things CSS cannot:

  • Search by text — //button[text()="Submit"] (CSS has no text selector).
  • Traverse upwards and sideways — select a parent, ancestor, or following sibling of a known element.
  • Use boolean logic — combine conditions with and / or / not().

What problem it solves

When a stable, unique attribute does not exist and CSS cannot express the relationship, XPath lets you describe the element by its position, text, or neighbours. For example: "the Delete button inside the row whose name cell says 'Ada'".

Where it is commonly used

  • Playwright tests, via page.locator('xpath=//...').
  • Browser DevTools (the $x() console helper) for quick DOM inspection.
  • Selenium, Appium, and other automation tools that accept XPath locators.
  • XML processing (XSLT, XQuery, config transforms) — outside the browser.

When a tester should use it

Use XPath as a fallback, not a default. Playwright's own guidance is to prefer user-facing locators (getByRole, getByLabel, getByText, getByTestId). Reach for XPath when: you must locate by exact text, you need parent/sibling navigation CSS cannot express, or you are maintaining an existing XPath-based suite.

XPath 1.0 only Browsers implement XPath 1.0. Functions from later specs such as matches(), ends-with(), and lower-case() are XPath 2.0+ and will throw a syntax error in a browser. Use contains(), starts-with(), translate(), and normalize-space() instead.

02Syntax

Basic form

//tag[predicate]/child::tag[@attribute="value"]

Broken down for //div[@class="card"]/a[contains(@href, "/product/")]:

PartMeaning
//Relative path — search from anywhere in the document (descendant-or-self).
/Absolute path — start at the document root.

Absolute vs relative A single leading / starts at the document root, so /html/body/div[3]/table breaks the moment markup changes. The double slash // means "anywhere below", which is almost always what you want.

//button                       // any button, anywhere
//div[@id="main"]              // div whose id is exactly "main"
//*[@data-qa="submit"]         // any element carrying a data attribute
//a[text()="Read more"]        // anchor whose full text is "Read more"
//input[@type="text"][1]       // the first text input among the matches
//li[last()]                   // the last li in each parent
//span[normalize-space()="Ok"] // compare ignoring surrounding whitespace
(//div[@class="card"])[3]      // the 3rd card among all matches (parenthesised)
//ul/li[2]/following-sibling::li  // siblings after the 2nd li
Index placement matters //ul/li[2] means "the 2nd li within each ul". (//ul/li)[2] means "the 2nd li across the whole document". Wrap the expression in parentheses when you want a global index.

03XPath in Playwright

Playwright ships an xpath selector engine. You pass an XPath expression to locator(), and it returns a normal locator that supports all the usual actions and assertions.

// Explicit engine prefix
const submit = page.locator('xpath=//button[@type="submit"]');

// Auto-detected: expressions starting with // or .. are treated as XPath
const title = page.locator('//h1');

// Chained: scope XPath to the result of a previous locator
const price = page.locator('.product-card').locator('xpath=.//span[@class="price"]');

Key facts

  • Strict mode applies. If an XPath matches more than one element, actions and assertions throw a strict-mode violation. Narrow the expression or use .first() / .nth().
  • Auto-waiting applies. XPath locators are auto-waited just like CSS locators — no manual sleeps.
  • It is the browser's engine. Expressions are evaluated by document.evaluate(), so only XPath 1.0 is supported.
  • XPath does not pierce shadow DOM. Playwright's CSS engine does cross open shadow roots; XPath does not. For shadow DOM use role/text/CSS locators.
  • Use a relative prefix in chains. After a chained locator, start with .// or ./ so the search stays scoped to that element.
page.$x() is deprecated Older examples use await page.$x('//button'), which returned an array of ElementHandles. That API is deprecated and has since been removed — migrate to page.locator('xpath=//button'). The modern locator is auto-waiting, retrying, and works with expect.

Using XPath with assertions

await expect(page.locator('xpath=//h1')).toHaveText('Dashboard');
await expect(page.locator('xpath=//ul/li')).toHaveCount(3);
await expect(page.locator('xpath=//button[@type="submit"]')).toBeEnabled();

Prefer CSS or user-facing locators first

Best: user-facing

getByRole('button', { name: 'Save' }) — stable, accessible, readable.

Good: test id / CSS

getByTestId('save-btn') or locator('.card .title') — fast and concise.

Fallback: XPath

locator('xpath=//td[text()="Ada"]/..') — when text or traversal is required.

06Detailed Explanation of Key Functions

Expand any function for its full description. Use the buttons to open or close all entries.

contains()
Purpose
Returns true when the first string argument contains the second anywhere inside it. It is the workhorse of resilient XPath, because it does not require an exact match.
Syntax
contains(haystack, needle)
Parameters
haystack — the string to search (often @class, @href, or text()). needle — the substring to find. Both are strings.
Return / Result
A boolean used as a predicate, keeping only the nodes for which it is true.
Example
await page.locator('xpath=//button[contains(@class,"btn-primary")]').click();
await page.locator('xpath=//a[contains(@href,"/products/")]').first().click();
Expected Result
Matches every button whose class attribute includes btn-primary, and every product link.
Common Usage
Partial class, id, href, data-attribute, and text matching when values carry dynamic suffixes.
Important Notes
It is a plain substring test, so contains(@class,"card") also matches card-header and discard if present. Add a space (" card ") or use normalize-space() on a token when exactness matters.
starts-with()
Purpose
Returns true when a string begins with the given prefix. Useful for generated ids and URLs that share a stable prefix.
Syntax
starts-with(string, prefix)
Parameters
string — value to test; prefix — the required leading substring.
Return / Result
Boolean, used as a predicate.
Example
await page.locator('xpath=//input[starts-with(@id,"user-")]').fill('ada');
Expected Result
Matches the input whose id starts with user-, e.g. user-email or user-name.
Common Usage
Framework-generated ids (react-select-1-input), route prefixes, and versioned asset URLs.
Important Notes
There is no ends-with() in XPath 1.0. To match a suffix, combine substring() and string-length().
normalize-space()
Purpose
Trims leading and trailing whitespace and collapses internal runs of whitespace to a single space, returning a clean string for comparison.
Syntax
normalize-space([string])
Parameters
Optional node or string. With no argument it normalises the string value of the current node.
Return / Result
A normalised string, compared against the literal in the predicate.
Example
await page.locator('xpath=//button[normalize-space()="Save changes"]').click();
Expected Result
Matches the button even when the markup contains extra spaces or newlines around its label.
Common Usage
Text-based matching where the DOM comes from a template with indentation or line breaks.
Important Notes
The most common cause of "working in DevTools but failing in the test" text XPath. Prefer it over raw text() comparisons.
text()
Purpose
A node test that selects the text nodes of an element, used to filter elements by their textual content.
Syntax
//tag[text()="value"]
//tag[contains(text(), "value")]
Parameters
None — it is a node test. Comparison happens against the string in the predicate.
Return / Result
A node set of text nodes. Used in a predicate it yields a boolean filter.
Example
await page.locator('xpath=//td[text()="Ada"]/..').getByRole('button', { name: 'Edit' }).click();
Expected Result
Finds the table row containing the cell "Ada" and clicks its Edit button.
Common Usage
Locating a row, card, or list item by a known label, then acting on a child control.
Important Notes
text() matches only direct text children. If the label is wrapped in a <span>, use contains(., "Ada") (dot = string value of all descendants) instead.
last()
Purpose
Returns the number of nodes in the current context node set. In a predicate it selects the final node(s).
Syntax
//li[last()]
//li[last()-1]
Parameters
None — it takes no arguments.
Return / Result
A number equal to the size of the context set. Enables indexing from the end.
Example
await page.locator('xpath=//table//tr[last()]/td[1]').click();
Expected Result
Targets the first cell of the last row of a table.
Common Usage
Selecting the most recently added row or item in a dynamically growing list.
Important Notes
last() is per context. In //ul/li[last()] it means the last li of each ul. Wrap in parentheses for a global "last of all".
position()
Purpose
Returns the 1-based index of the current node within its context node set, enabling range and parity selection.
Syntax
//li[position() = 2]
//li[position() <= 3]
//tr[position() mod 2 = 0]
Parameters
None. It is a number function evaluated per node during the predicate.
Return / Result
A number from 1 to the size of the set.
Example
await expect(page.locator('xpath=//tbody/tr[position() <= 5]')).toHaveCount(5);
Expected Result
Matches the first five body rows and asserts there are exactly five.
Common Usage
Pagination assertions, "first N items", alternating-row (even/odd) logic.
Important Notes
Numbers in a predicate are shorthand for position() = n, so [2] and [position()=2] are equivalent.
count()
Purpose
Counts the nodes in a node set. Used inside a predicate it lets you reason about quantities of elements.
Syntax
count(node-set)
Parameters
A node set, e.g. //li or .//span.
Return / Result
A number.
Example
await page.locator('xpath=//div[count(.//li) > 2]').first().click();
Expected Result
Matches the first container holding more than two list items.
Common Usage
Rare: for asserting a count in tests, prefer Playwright's toHaveCount() on a locator, which gives clearer failures.
Important Notes
count() returns a number that cannot be used directly in a Playwright assertion — it only filters nodes. Use await expect(loc).toHaveCount(n) for count assertions.
not()
Purpose
Boolean negation. Keeps nodes for which the inner expression is false.
Syntax
not(expression)
Parameters
Any boolean-producing expression, e.g. @disabled or contains(@class,"hidden").
Return / Result
Boolean, inverted.
Example
await expect(page.locator('xpath=//button[not(@disabled)]')).toHaveCount(3);
Expected Result
Asserts that exactly three enabled buttons are present.
Common Usage
Selecting the first interactive control, or excluding hidden/disabled/hidden-by-class elements.
Important Notes
not(contains(@class,"x")) is true when the attribute is absent too, which is usually the intent, but be explicit if it is not.
Parent & sibling navigation (axes)
Purpose
Move up or sideways through the tree from a known anchor element — something CSS cannot express directly.
Syntax
//anchor/parent::tag
//anchor/ancestor::tag
//anchor/following-sibling::tag[1]
//anchor/preceding-sibling::tag[1]
Parameters
The axis determines direction; the following node test and optional predicate narrow the result.
Return / Result
A node set of the requested relatives.
Example
await page.locator(
  'xpath=//td[normalize-space()="Ada"]/parent::tr//button[@data-action="delete"]'
).click();
Expected Result
Finds the row containing "Ada" and clicks its delete button.
Common Usage
Row-scoped actions, selecting a form input from its label, or the error message after a field.
Important Notes
Add [1] to following-sibling / preceding-sibling when you want the nearest one, since without it the axis returns all matching siblings.
translate() — case-insensitive matching
Purpose
Replaces characters in one string with the corresponding characters from another. Commonly abused to implement a case-insensitive comparison, since XPath 1.0 has no lower-case().
Syntax
translate(string, fromChars, toChars)
Parameters
string to transform; fromChars the characters to replace; toChars their replacements. Characters present in fromChars but past the end of toChars are removed.
Return / Result
The transformed string.
Example
await page.locator(
  'xpath=//div[translate(@data-state,"ACTIVE","active")="active"]'
).click();
Expected Result
Matches the element regardless of the case used in the data-state attribute.
Common Usage
Case-insensitive matching of class names, statuses, and text.
Important Notes
Only translates the exact characters you list — you must include both uppercase and lowercase sets for full case-insensitivity. It is verbose, so prefer a stable lowercase attribute when one exists.

07Practical Examples

Example 1 — Basic Usage

The simplest XPath locator: find a button by its id and click it.

import { test, expect } from '@playwright/test';

test('click a button located with XPath', async ({ page }) => {
  await page.goto('https://example.com');

  const login = page.locator('xpath=//button[@id="login"]');
  await expect(login).toBeVisible();
  await login.click();
});

Example 2 — Real-World Usage

A login flow using text and attribute XPath, with assertions on the outcome.

import { test, expect } from '@playwright/test';

test('user can log in (XPath locators)', async ({ page }) => {
  await page.goto('https://demo.example.com/login');

  await page.locator('xpath=//input[@type="email"]').fill('qa@example.com');
  await page.locator('xpath=//input[@name="password"]').fill('secret123');
  await page.locator('xpath=//button[normalize-space()="Log in"]').click();

  await expect(page).toHaveURL(/\/dashboard/);
  await expect(page.locator('xpath=//h1[contains(., "Welcome")]')).toBeVisible();
});

Example 3 — Multiple Functions

Combining contains(), starts-with(), normalize-space(), predicates, and axes in one search.

import { test, expect } from '@playwright/test';

test('filter the order table', async ({ page }) => {
  await page.goto('/orders');

  // Rows whose status cell contains "shipped" and whose id starts with "ORD-"
  const shipped = page.locator(
    'xpath=//tr[starts-with(@id,"ORD-") and contains(@data-status,"shipped")]'
  );
  await expect(shipped).toHaveCount(3);

  // The action button in the row labelled "Ada"
  await page.locator(
    'xpath=//td[normalize-space()="Ada"]/parent::tr//button[text()="View"]'
  ).click();

  await expect(page.locator('xpath=//h2[contains(text(),"Order details")]')).toBeVisible();
});

Example 4 — Negative Scenario

An XPath that looks correct but matches nothing, with the reason why.

import { test, expect } from '@playwright/test';

test('this XPath fails on purpose', async ({ page }) => {
  await page.goto('https://example.com');

  // Markup is: <button> Submit </button>  (note the surrounding spaces)
  await expect(page.locator('xpath=//button[text()="Submit"]')).toBeVisible();
});

Why it fails: text()="Submit" requires an exact match including whitespace, but the text node is " Submit ". The assertion retries until the timeout and then fails with a "waiting for locator" message. Fix it with //button[normalize-space()="Submit"] or //button[contains(., "Submit")].

Example 5 — Advanced Usage

Chained and scoped XPath, positional predicates, global indexing, and a polled assertion.

import { test, expect } from '@playwright/test';

test('advanced XPath techniques', async ({ page }) => {
  await page.goto('/catalogue');

  const firstCard = page.locator('xpath=(//div[@class="card"])[1]');

  // Chain: keep the XPath relative to the card
  await expect(firstCard.locator('xpath=.//h3')).toContainText('Laptop');
  await firstCard.locator('xpath=.//button[@data-action="add"]').click();

  // Positional range within one container
  await expect(page.locator('xpath=//ul[@id="cart"]/li[position() <= 3]')).toHaveCount(3);

  // Last row added to the cart
  const lastRow = page.locator('xpath=//table[@id="cart"]//tr[last()]');
  await expect(lastRow).toContainText('Laptop');

  // Sibling navigation: the badge next to the "Cart" heading
  const badge = page.locator('xpath=//h2[normalize-space()="Cart"]/following-sibling::span[1]');
  await expect(badge).toBeVisible();

  // Poll a non-locator value
  await expect.poll(async () => await page.locator('xpath=//ul[@id="cart"]/li').count())
    .toBe(1);
});

08Before vs After

Playwright removed the old page.$x() API in favour of XPath locators. This is a genuine migration every XPath-based suite faces.

Without locators (deprecated page.$x())

// Old approach: returns ElementHandles, no auto-waiting, no assertions
import { test, expect } from '@playwright/test';

test('old style', async ({ page }) => {
  await page.goto('/inbox');

  const [handle] = await page.$x('//button[text()="Compose"]');
  await handle.click();

  const body = await page.$x('//div[@class="status"]');
  expect(await body[0].textContent()).toBe('Ready'); // no retry: flaky
});

With XPath locators (current API)

// Modern approach: auto-waiting locator + retrying assertion
import { test, expect } from '@playwright/test';

test('new style', async ({ page }) => {
  await page.goto('/inbox');

  await page.locator('xpath=//button[normalize-space()="Compose"]').click();

  await expect(page.locator('xpath=//div[@class="status"]')).toHaveText('Ready');
});

Why the "after" version is better

  • Auto-waiting — the locator waits for the element to be actionable; the old handle was resolved once and could go stale.
  • Retrying assertions — toHaveText() retries; reading textContent() once does not.
  • Strict mode — an ambiguous XPath fails loudly instead of silently using the first match.
  • Uniform API — XPath locators compose with .first(), .filter(), chaining, and every Playwright action.

10Best Practices

  1. Prefer user-facing locators first. Use getByRole / getByLabel / getByTestId before reaching for XPath.
  2. Always use relative paths. Start with // or .//, never /html/body/....
  3. Anchor on a stable attribute or a test id. [@data-testid="x"] beats structural position.
  4. Prefer normalize-space() for text. It absorbs the whitespace that templates introduce.
  5. Match a distinctive substring, not full sentences. contains(., "shipped") survives copy changes.
  6. Avoid positional predicates when a unique attribute exists. Positions shift when rows are added or removed.
  7. Keep expressions short. A long XPath is a brittle locator that will be hard to debug.
  8. Scope chained XPath with .//. It keeps the search inside the parent element.
  9. Aim for exactly one match. Respect strict mode rather than papering over it with .first().
  10. Remember XPath 1.0 only. Do not use 2.0 functions in a browser context.
  11. Do not use XPath to cross shadow DOM. Switch to CSS or role-based locators there.
  12. Keep XPath out of page objects' internals where possible. Isolate fragile expressions in one place so they are easy to update.

11Interview Questions

Beginner Questions

1. What is XPath and how does Playwright evaluate it?
XPath is a W3C language for selecting nodes in an XML/HTML document. Playwright passes the expression to the browser, which evaluates it with document.evaluate(), and returns a locator.
2. How do you use an XPath in a Playwright locator?
Pass it to locator(): page.locator('xpath=//button[@id="login"]'). Expressions beginning with // or .. are auto-detected as XPath.
3. What is the difference between / and //?
A single / starts at the document root (absolute). // searches any descendant of the current context (relative), which is far more resilient.
4. How do you find an element by its text?
//button[text()="Submit"] for an exact match, or //button[normalize-space()="Submit"] to ignore surrounding whitespace.
5. What does @ mean in XPath?
It is shorthand for the attribute axis, so [@id="x"] tests the id attribute of the current node.

Intermediate Questions

1. Why does //button[text()="Submit"] fail when the button clearly says Submit?
Very often the text node has leading or trailing whitespace, or the label is wrapped in a child element so it is not a direct text child. Use normalize-space() or contains(., "Submit").
2. What is the difference between //ul/li[2] and (//ul/li)[2]?
The first selects the 2nd li within each ul. The second selects the 2nd li across the whole document, because parentheses turn the whole set into the context.
3. How do you select the parent of an element in XPath, and why can't CSS do it?
With the parent axis: //td[text()="Ada"]/... CSS selectors match downward only, so they have no general parent selector; XPath can traverse any axis.
4. Which XPath version do browsers support, and what does that restrict?
XPath 1.0 only. Functions from 2.0 such as matches(), ends-with(), and lower-case() are unavailable; use contains(), translate(), and substring() workarounds.
5. How does Playwright's strict mode affect XPath locators?
If an XPath resolves to more than one element, actions and assertions throw a strict-mode violation. You must narrow the expression or resolve it explicitly with .first() / .nth().

Advanced Questions

1. How do you match a class token exactly with contains(@class)?
Pad the attribute with spaces so the token cannot match as a substring: contains(concat(" ", normalize-space(@class), " "), " card ").
2. Why should a chained XPath start with .// rather than //?
Because // restarts the search from the document root, escaping the parent locator's scope. .// keeps it relative to the element the chained locator resolves to.
3. Why can XPath not locate elements inside a shadow root, and what do you use instead?
XPath is evaluated against a document's node tree, and shadow roots are separate trees that document.evaluate() traversal does not cross by default. Playwright's CSS engine pierces open shadow roots, and role/text locators work too — use those.
4. How would you migrate a suite that uses page.$x() to modern Playwright?
Replace each page.$x(expr) with page.locator('xpath=' + expr), drop the array-destructuring pattern, and use locator actions plus expect assertions so auto-waiting and retrying apply.
5. When is XPath the right choice over CSS or role-based locators?
When you must locate by exact text, need upward or sibling traversal that CSS cannot express, or are maintaining an existing XPath suite. Otherwise role/test-id locators are preferred for stability and readability.

14Key Takeaways

  • XPath is a node-selection language evaluated by the browser's XPath 1.0 engine; in Playwright you use it through locator('xpath=...').
  • Use relative paths (//, .//) and anchor on stable attributes or test ids — never absolute /html/body paths.
  • text() is exact and only matches direct text children; reach for normalize-space() and contains(., ...) for real-world text.
  • XPath's advantage over CSS is traversal — parents, ancestors, and siblings — and text-based matching.
  • Browsers only support XPath 1.0: no matches(), ends-with(), or lower-case().
  • Playwright's strict mode applies to XPath: an expression matching multiple elements is an error, not a first-match shortcut.
  • page.$x() is gone — migrate to locators so you get auto-waiting, retrying assertions, and chaining.
  • XPath cannot pierce shadow DOM; use CSS or role-based locators there, and prefer user-facing locators generally.
