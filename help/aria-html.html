Accessibility Reference

ARIA in HTML

WAI-ARIA roles, states, and properties used with HTML — what they do, when they are appropriate, and why native HTML elements usually win.

WAI-ARIA 1.2 HTML + JavaScript role / aria-* WCAG 2.2 Beginner → Advanced

01What Is It?

ARIA (Accessible Rich Internet Applications), formally WAI-ARIA, is a W3C specification that lets you add accessibility semantics to HTML: a role says what an element is, and aria-* states and properties describe its current condition. Browsers turn those semantics into the accessibility tree that assistive technologies such as screen readers consume.

ARIA is expressed entirely through attributes. It is markup that annotates the DOM — it is not a separate language, and it adds no behaviour of its own.

<!-- Semantics only: this claims "button" but behaves like a div -->
<div role="button" tabindex="0" aria-pressed="false">Mute</div>

Why it exists

HTML has a fixed vocabulary. When you build a custom widget out of generic <div> and <span> elements, the markup carries no meaning: a screen reader sees anonymous text with no idea that it is a button, tab, slider, or dialog. ARIA fills that gap by supplying the missing role and the state information that a custom widget needs to be usable non-visually.

What problem it solves

  • Naming — gives an accessible name to controls that have no visible label, such as an icon-only button.
  • Semantics — describes composite widgets (tabs, menus, grids, trees, comboboxes) that HTML has no native element for.
  • State — communicates dynamic conditions like expanded, checked, selected, busy, invalid, and current.
  • Live updates — announces content that changes without a page reload (live regions).

Where it is commonly used

  • Reusable component libraries (design systems) that build custom buttons, dialogs, tabs, and menus.
  • Single-page applications where the DOM is rewritten by JavaScript.
  • Icon-only controls, loading states, toasts, and validation messages.
  • Landmark landmarks on complex page layouts so screen reader users can jump between regions.
  • Automated tests: Playwright's getByRole(), toHaveAccessibleName(), and toHaveRole() read exactly these semantics.

When a developer should use it

Use ARIA after you have exhausted native HTML, never before. The W3C's own guidance is blunt: "No ARIA is better than bad ARIA." Reach for ARIA when (a) no HTML element provides the required role or state, (b) you are composing a custom widget, or (c) you need to describe a dynamic state that native HTML cannot express. If a native element already does the job, adding ARIA is redundant at best and contradictory at worst.

ARIA does not add behaviour Adding role="button" to a <div> does not make it focusable, clickable, or keyboard-operable. ARIA only changes what assistive technology is told. You must supply focus handling and keyboard events in JavaScript yourself.
Versions This page targets WAI-ARIA 1.2 (W3C Recommendation, June 2023), the version implemented by current browsers. ARIA 1.1 added aria-details, aria-errormessage, aria-keyshortcuts, and aria-modal. aria-description is an ARIA 1.3 addition with limited support — use aria-describedby when broad support matters.

02Syntax

Basic form

<element role="ROLE" aria-STATE="VALUE">content</element>

ARIA is written as ordinary HTML attributes. role and every aria-* attribute are global HTML attributes — they are valid on any element, though they are only meaningful on the roles that allow them.

<!-- 1. Role: what the element is -->
<div role="tablist">

  <!-- 2. Composite widget: a tab controlled by aria-selected -->
  <button role="tab" id="tab-a" aria-selected="true" aria-controls="panel-a">Overview</button>
  <button role="tab" id="tab-b" aria-selected="false" aria-controls="panel-b" tabindex="-1">Details</button>
</div>

<!-- 3. The panel the tab points at -->
<div role="tabpanel" id="panel-a" aria-labelledby="tab-a">Overview content</div>

Breaking down the parts

PartMeaning
roleA single token naming the element's type, e.g. button, navigation, dialog. The first recognised token in the list wins; unknown values are ignored.
aria-*A state or property. Names are lowercase, hyphen-separated, and always prefixed with aria-.
Attribute valueUsually a token ("true", "polite", "mixed"), a number, a string, or a space-separated list of element ids for reference attributes.
id / aria-labelledbyReference attributes point at other elements by id. The referenced element's text becomes the name or description.
tabindexNot ARIA, but the companion attribute that makes a custom widget reachable by keyboard.
Role wins over the element Once you set role, assistive technology stops treating the element as its native type. <button role="heading"> is announced as a heading, not a button — a semantic contradiction you should never create.

Value formats

aria-hidden="true"                 // boolean token: "true" | "false"
aria-live="polite"                 // enumerated token: off | polite | assertive
aria-checked="mixed"               // tri-state enum: true | false | mixed
aria-level="2"                     // integer
aria-valuenow="42"                 // number
aria-label="Close dialog"          // free text
aria-labelledby="title close-btn"  // ID reference list (space separated)
aria-keyshortcuts="Control+S"      // keystroke string

Attribute kinds

KindDefinitionExamples
RoleWhat the element is; the anchor for every other ARIA attribute.role="dialog"
StateCan change during the page's lifetime; usually updated by JavaScript in response to user action.aria-expanded, aria-checked, aria-selected
PropertyDescribes a relatively stable characteristic of the element.aria-label, aria-describedby, aria-required
GlobalApplicable to essentially every role.aria-hidden, aria-label, aria-live, aria-controls
State vs property is pragmatic, not absolute The spec classifies many attributes in both camps. The practical question is whether the value changes at runtime — if it does, keep it in sync with the visual state, because a stale ARIA value is worse than no value.

03ARIA in HTML

The HTML Accessibility API Mappings (HTML-AAM) define a default ARIA role for most HTML elements. That default is why the first rule of ARIA is to prefer native HTML: the role is already applied for you, and the browser supplies focus, keyboard, and form behaviour as well.

Native elements already have implicit roles

<button>buttonRedundant (role="button" adds nothing)
<a href>linkRedundant

<h1>–<h6>heading (level 1–6)Redundant

Where ARIA genuinely adds value

Tabs, menus, trees, grids, comboboxes—Composite widget roles
Announce dynamic messages—role="status" / aria-live
Mark the current page in navigation—aria-current="page"
Modal dialog isolation<dialog> + showModal()role="dialog" aria-modal="true"

The five rules of ARIA

  1. Use native HTML first. If a native element or attribute already provides the semantics and behaviour, use it instead of repurposing an element with a role.
  2. Do not change native semantics unless you truly must. Avoid <button role="link"> and <h2 role="button">.
  3. All interactive ARIA widgets must be keyboard operable. A role without keyboard support is unusable by keyboard and screen reader users.
  4. Never use role="presentation" or aria-hidden="true" on a focusable element. It creates content that receives focus but cannot be perceived.
  5. Every interactive element must have an accessible name. An unnamed button is announced as just "button".
Landmarks come almost free Using <header>, <nav>, <main>, <aside>, and <footer> gives screen reader users landmark navigation with no ARIA at all. Reserve role="region" for named <section> elements that are worth jumping to.

06Accessible Names & Descriptions

An accessible name is the label a screen reader speaks for a control. The name computation algorithm follows a fixed precedence, and ARIA attributes sit near the top of it.

Name precedence (highest first)

PrioritySourceExample
1aria-labelledby — text of the referenced element(s)aria-labelledby="nav-heading"
2aria-label — a literal stringaria-label="Close"
3Native labelling: <label>, <legend>, <caption>, alt, or the element's own text content<label for="email">Email</label>
4title attribute (weak fallback)title="Close"
Higher priority silently wins If you set both aria-label="Save" and aria-labelledby="save-heading", the referenced heading wins — the aria-label is ignored, not merged. Likewise an empty aria-label="" can erase a perfectly good native name.

Names vs descriptions

  • Name — a short identifier spoken when focus lands. Sources: aria-labelledby, aria-label, native labels, title.
  • Description — extra guidance spoken after a short pause, or on demand. Sources: aria-describedby, then title.
<button aria-label="Close dialog">
  <svg aria-hidden="true">...</svg>
</button>

<label for="pwd">Password</label>
<input id="pwd" type="password" aria-describedby="pwd-hint" aria-required="true" />
<p id="pwd-hint">At least 12 characters.</p>

<nav aria-labelledby="primary-nav">
  <h2 id="primary-nav">Primary</h2>
  <ul>...</ul>
</nav>
Referenced elements may be visually hidden An element referenced by aria-labelledby or aria-describedby still contributes its text even when hidden with display:none or aria-hidden="true". That is useful for reusable hidden headings — and a common source of accidental duplication when you forget a reference is still live.

07Live Regions

A live region is a part of the page that announces its own changes. Because screen reader users cannot see a toast or an inline error appear, a live region tells them that new content exists without moving focus.

AttributeValuesEffect
aria-liveoffAnnouncements disabled (default).
aria-livepoliteAnnounced when the user is idle — use for statuses and results.
aria-liveassertiveInterrupts immediately — reserve for urgent errors.
aria-atomictrueAnnounce the entire region, not just the changed node.
aria-relevantadditions, removals, text, allWhich mutations trigger an announcement.
aria-busytrueBatch changes; announce once the region is marked not busy.

Role shortcuts

  • role="status" — polite, atomic. Ideal for "Saved", "3 results found".
  • role="alert" — assertive, atomic. Ideal for blocking errors.
  • role="log" — polite, non-atomic. Ideal for a chat or activity feed.
<!-- The region must exist in the DOM before you change it -->
<p id="status" role="status" aria-live="polite"></p>

<script>
  document.getElementById('status').textContent = '3 results found.';
</script>
The classic mistake Creating an element and filling it in the same tick often produces no announcement, because the live region did not exist when its content changed. Insert an empty region first, then update its text in a separate step.

08Detailed Reference

The entries below cover the roles and attributes you will reach for most often, with syntax, values, examples, and the pitfalls that trip people up. Expand an entry to read it.

Roles

role="button"
Purpose
Declares an element as a clickable action, so assistive technology announces "button" instead of anonymous text.
Syntax
<div role="button" tabindex="0">Save</div>
Parameters
No parameters. Pair with a name (aria-label or text content), tabindex="0" for focusability, and optional aria-pressed or aria-expanded.
Return / Result
Exposes the element in the accessibility tree with the button role and its computed name.
Example
<div role="button" tabindex="0" id="save" aria-pressed="false">Save</div>

<script>
  const save = document.getElementById('save');
  save.addEventListener('click', toggle);
  save.addEventListener('keydown', function (e) {
    if (e.key === 'Enter' || e.key === ' ') {
      e.preventDefault();
      toggle();
    }
  });
  function toggle() {
    const pressed = save.getAttribute('aria-pressed') === 'true';
    save.setAttribute('aria-pressed', String(!pressed));
  }
</script>
Expected Result
The element is focusable with Tab, activated by Enter or Space, and announced as "Save, button, not pressed".
Common Usage
Only in frameworks or design systems that must render custom markup. In plain HTML, use <button>, which is focusable, keyboard-operable, and styled already.
Important Notes
ARIA gives you no keyboard behaviour: without the keydown handler, Enter and Space do nothing. A <button> handles all of this for free, so it is the correct choice in almost every case.
role="dialog" & aria-modal
Purpose
Marks an overlay window, so screen readers announce the dialog and read its contents.
Syntax
<div role="dialog" aria-modal="true" aria-labelledby="dlg-title" aria-describedby="dlg-desc">...</div>
Parameters
aria-modal="true" tells assistive technology the rest of the page is inert. aria-labelledby supplies the name; aria-describedby supplies an optional description.
Return / Result
Traps reading context inside the dialog and exposes its name and description.
Example
<dialog id="confirm" aria-labelledby="confirm-title">
  <h2 id="confirm-title">Delete this file?</h2>
  <p>This action cannot be undone.</p>
  <button data-action="cancel">Cancel</button>
  <button data-action="delete">Delete</button>
</dialog>

<script>
  document.getElementById('confirm').showModal();
</script>
Expected Result
The dialog receives focus, the rest of the page is hidden from assistive technology, and Esc closes the native <dialog>.
Common Usage
Confirmation prompts, settings panels, command palettes, and any overlay that should hold attention.
Important Notes
aria-modal="true" does not make the dialog modal — it only reports that it is. You or the native <dialog> element must actually trap focus, block background interaction, and restore focus on close.
role="tablist" / role="tab" / role="tabpanel"
Purpose
Builds a tabbed interface: a list of tabs, one selected at a time, each controlling a panel.
Syntax
<div role="tablist" aria-label="Sections">
  <button role="tab" aria-selected="true"  aria-controls="p1" id="t1">One</button>
  <button role="tab" aria-selected="false" aria-controls="p2" id="t2" tabindex="-1">Two</button>
</div>
<div role="tabpanel" id="p1" aria-labelledby="t1" tabindex="0">Panel one</div>
<div role="tabpanel" id="p2" aria-labelledby="t2" tabindex="0" hidden>Panel two</div>
Parameters
aria-selected on the active tab; aria-controls links a tab to its panel; aria-labelledby on the panel points back at its tab.
Return / Result
Announces "One, tab, 1 of 2, selected" and lets users move between tabs with the arrow keys.
Example
tablist.addEventListener('keydown', function (e) {
  const tabs = Array.from(tablist.querySelectorAll('[role="tab"]'));
  const i = tabs.indexOf(document.activeElement);
  if (i === -1) return;
  let next = null;
  if (e.key === 'ArrowRight') next = tabs[(i + 1) % tabs.length];
  if (e.key === 'ArrowLeft')  next = tabs[(i - 1 + tabs.length) % tabs.length];
  if (e.key === 'Home')       next = tabs[0];
  if (e.key === 'End')        next = tabs[tabs.length - 1];
  if (next) { e.preventDefault(); next.focus(); next.click(); }
});
Expected Result
Arrow keys cycle through tabs, Home and End jump to the ends, and the selected tab's panel is shown.
Common Usage
Multi-section settings pages, dashboards, and any "one panel at a time" pattern.
Important Notes
The tablist uses roving tabindex — only the selected tab is in the tab order (tabindex="0"); the rest are tabindex="-1". Give the tabpanel tabindex="0" only when it has no focusable content of its own.
role="checkbox" / role="switch"
Purpose
Represents a boolean control. A switch is announced as "on/off"; a checkbox as "checked/unchecked" and supports the third mixed state.
Syntax
<div role="checkbox" aria-checked="false" tabindex="0">Subscribe</div>
<button role="switch" aria-checked="true">Dark mode</button>
Parameters
aria-checked is required and takes true, false, or (checkbox only) mixed.
Return / Result
The control is announced with its checked state, and the state changes when the user toggles it.
Example
<div role="checkbox" aria-checked="false" tabindex="0" id="subscribe">Subscribe</div>
<script>
  const box = document.getElementById('subscribe');
  function toggle() {
    const on = box.getAttribute('aria-checked') === 'true';
    box.setAttribute('aria-checked', String(!on));
  }
  box.addEventListener('click', toggle);
  box.addEventListener('keydown', function (e) {
    if (e.key === ' ') { e.preventDefault(); toggle(); }
  });
</script>
Expected Result
Space toggles the state and the screen reader announces "checked" or "not checked".
Common Usage
Custom toggles in design systems, and tri-state parent checkboxes in trees.
Important Notes
Prefer <input type="checkbox">: it is focusable, toggleable, and participates in forms. On a native checkbox, adding aria-checked is redundant and easily desynchronises from the real checked property. mixed is invalid on role="switch".
role="alert" & role="status"
Purpose
Live regions that announce content changes without moving focus. alert is assertive; status is polite.
Syntax
<div role="alert"></div>
<div role="status"></div>
Parameters
None required. role="alert" implies aria-live="assertive" and aria-atomic="true"; role="status" implies polite and atomic.
Return / Result
Any text added to the region is announced by the screen reader.
Example
<div id="toast" role="status"></div>
<script>
  document.getElementById('toast').textContent = 'Profile saved.';
</script>
Expected Result
The message is spoken politely, without interrupting the user, and without stealing focus.
Common Usage
Form success messages, "N results found" counters, inline validation errors, chat activity.
Important Notes
The live region must be in the DOM before its content changes, or nothing is announced. Use assertive sparingly — overusing it makes a page interrupt constantly and is a serious usability problem.
role="presentation" / role="none"
Purpose
Removes an element's implicit semantics, so it is exposed as generic content.
Syntax
<table role="presentation">...</table>
Parameters
No values — presentation and none are synonyms since ARIA 1.1.
Return / Result
The element no longer appears as a table, list, image, or similar in the accessibility tree.
Example
<!-- Layout table used purely for positioning -->
<table role="presentation">
  <tr><td>Logo</td><td>Navigation</td></tr>
</table>
Expected Result
Screen readers skip the table semantics and read the content in document order.
Common Usage
Layout tables, decorative images that cannot be expressed as CSS backgrounds, and removing semantics from wrapper elements.
Important Notes
Never use it on a focusable or interactive element. Presentation is inherited by an element's required owned children (a presentational <ul> makes its <li>s presentational too), but not by generic descendants. If the element has any global ARIA attribute or is focusable, the role is ignored.

Attributes

aria-label
Purpose
Provides an accessible name as a literal string when no visible text label exists.
Syntax
<button aria-label="Close"><svg aria-hidden="true">...</svg></button>
Parameters
A non-empty string. Use it on roles that support naming: buttons, links, landmarks, form controls, tables, images.
Return / Result
Sets the element's accessible name, taking precedence over native labels but losing to aria-labelledby.
Example
<nav aria-label="Breadcrumb">
  <ol>...</ol>
</nav>

<button aria-label="Increase quantity">+</button>
Expected Result
The control is announced as "Close, button" or "Breadcrumb, navigation" instead of an unlabelled widget.
Common Usage
Icon-only buttons, repeated landmarks, "+"/"−" steppers, and search inputs without a visible label.
Important Notes
The string should match the visible label when one exists — otherwise voice-control users cannot activate it by saying what they see. Do not put a name on a plain <div> or <span> with no role; it is ignored. An empty value removes an existing name.
aria-labelledby
Purpose
Builds the accessible name from the text of one or more existing elements.
Syntax
<section aria-labelledby="s-title">
  <h2 id="s-title">Recent activity</h2>
</section>
Parameters
A space-separated list of element ids. Multiple ids are concatenated in order.
Return / Result
Sets the accessible name to the referenced text; takes precedence over aria-label and native labelling.
Example
<h3 id="q3">Shipping address</h3>
<input id="street" aria-labelledby="q3 street-label" />
<span id="street-label">Street</span>
Expected Result
The input is announced as "Shipping address Street".
Common Usage
Tying a dialog or section to its visible heading, naming form controls by adjacent text, and reusing an existing visible label.
Important Notes
Referenced elements still contribute text even if hidden, so a stale reference can silently duplicate a name. Broken ids simply fall through to the next naming source, which can mask a bug. Prefer this over aria-label when the label is already visible on screen.
aria-describedby
Purpose
Attaches supplementary description text to an element, without affecting its name.
Syntax
<input id="pin" aria-describedby="pin-hint pin-error" />
Parameters
A space-separated list of element ids whose text becomes the description.
Return / Result
Sets the accessible description (not the name), announced after a pause or on demand.
Example
<label for="pin">PIN</label>
<input id="pin" type="password" aria-describedby="pin-hint" />
<p id="pin-hint">Four digits, sent by post.</p>
Expected Result
The field is announced as "PIN, edit, Four digits, sent by post".
Common Usage
Format hints, character limits, help text, and inline error messages alongside the field.
Important Notes
Keep descriptions short — screen readers read them in full on every focus. For error text, pair it with aria-invalid="true" and consider aria-errormessage so the message is only surfaced while invalid.
aria-hidden
Purpose
Removes an element and its subtree from the accessibility tree while leaving it visible on screen.
Syntax
<svg aria-hidden="true" focusable="false">...</svg>
Parameters
true hides it; false (or absent) leaves it exposed.
Return / Result
The subtree is not announced and cannot be reached by screen reader navigation.
Example
<button>
  <svg aria-hidden="true" focusable="false" width="16" height="16">...</svg>
  Save
</button>
Expected Result
The button is read as "Save, button" with no mention of the decorative icon.
Common Usage
Decorative icons and images, duplicate text, off-screen overlay scaffolding, and hiding collapsed panels' contents from the tree.
Important Notes
It does not remove the element from the tab order. Hiding a focusable element produces "ghost" focus — a blank stop the user cannot identify. Use the inert attribute or display:none for that. Values other than "true" and "false" (for example "aria-hidden" with no value) are ignored.
aria-expanded
Purpose
Reports whether the content an element controls is currently shown or hidden.
Syntax
<button aria-expanded="false" aria-controls="menu-1">Menu</button>
<ul id="menu-1" hidden>...</ul>
Parameters
true (expanded) or false (collapsed, the default). Omit the attribute entirely when the element does not own expandable content.
Return / Result
Adds "expanded" or "collapsed" to the announced state.
Example
<button id="toggle" aria-expanded="false" aria-controls="panel">Details</button>
<div id="panel" hidden>Hidden content</div>
<script>
  const btn = document.getElementById('toggle');
  const panel = document.getElementById('panel');
  btn.addEventListener('click', function () {
    const open = btn.getAttribute('aria-expanded') === 'true';
    btn.setAttribute('aria-expanded', String(!open));
    panel.hidden = open;
  });
</script>
Expected Result
Each click toggles the panel and the announcement switches between "collapsed" and "expanded".
Common Usage
Disclosure widgets, accordions, hamburger menus, comboboxes, and tree items.
Important Notes
Never leave it static: an aria-expanded="true" that never changes misreports the interface. On a native <details> the browser manages this state for you, which is why the native element needs no ARIA at all.
aria-controls
Purpose
Identifies the element whose content or presence this element controls.
Syntax
<button aria-controls="panel-1" aria-expanded="false">Show</button>
Parameters
A space-separated list of element ids.
Return / Result
Records a relationship between the control and the region it affects.
Example
<button aria-expanded="false" aria-controls="filters">Filters</button>
<aside id="filters" hidden>...</aside>
Expected Result
Assistive technology can offer a shortcut to jump from the control to the region it affects.
Common Usage
Disclosure/accordion headers, tabs pointing at panels, and buttons that reveal menus.
Important Notes
Support is inconsistent: some screen readers ignore aria-controls entirely, so never make the relationship depend on it. Use it as an enhancement alongside visible state changes, and always pair it with aria-expanded for expandable content.
aria-current
Purpose
Marks the item within a set that represents the current position — most often the current page in navigation.
Syntax
<a href="/reports" aria-current="page">Reports</a>
Parameters
page, step, location, date, time, true, or false (the default).
Return / Result
Announces the item as "current page" (or the chosen token) rather than only showing it visually.
Example
<nav aria-label="Steps">
  <ol>
    <li><a href="#" aria-current="step">Address</a></li>
    <li><a href="#">Payment</a></li>
  </ol>
</nav>
Expected Result
The active link is announced as "Address, current step, link".
Common Usage
Site navigation, breadcrumbs, carousels, pagination, and multi-step wizards.
Important Notes
It conveys semantics only — you must still style the current item visually (for example with [aria-current] in CSS). Remember that href="#" in the example is a placeholder for a real URL in production.
aria-disabled
Purpose
Reports that an element is currently unavailable while keeping it discoverable and focusable.
Syntax
<button aria-disabled="true">Delete</button>
Parameters
true or false (the default).
Return / Result
The element is announced as "dimmed" or "unavailable" but is not removed from the tab order.
Example
<button id="delete" aria-disabled="true">Delete</button>
<script>
  document.getElementById('delete').addEventListener('click', function (e) {
    if (e.currentTarget.getAttribute('aria-disabled') === 'true') {
      e.preventDefault();
      return;
    }
    // perform the action
  });
</script>
Expected Result
The button stays focusable so keyboard users can discover why it is unavailable, and clicks are ignored.
Common Usage
Toolbar actions that are contextually unavailable, form submit buttons before validation passes, and composite widget items.
Important Notes
It enforces nothing: unlike the native disabled attribute, the click handler still fires, so you must guard the action yourself. Keeping controls focusable is generally better for discoverability than the native disabled, which removes them from the tab order entirely.
aria-invalid & aria-errormessage
Purpose
Report that a field's value failed validation, and point at the message explaining why.
Syntax
<input id="email" aria-invalid="true" aria-errormessage="email-error" />
<p id="email-error">Enter a valid email address.</p>
Parameters
aria-invalid: true, false (default), grammar, or spelling. aria-errormessage: the id of the error element.
Return / Result
The field is announced as invalid, and the referenced message is exposed as its error text.
Example
email.addEventListener('blur', function () {
  const bad = !email.validity.valid;
  email.setAttribute('aria-invalid', String(bad));
  error.hidden = !bad;
});
Expected Result
On invalid input the message appears visually and is announced with the field.
Common Usage
Form validation on blur or submit, in conjunction with a status/alert live region for the summary.
Important Notes
aria-errormessage is only honoured while aria-invalid="true"; support is still limited, so pair it with aria-describedby for the widest coverage. Do not remove the error styling when JavaScript fails — native constraint validation is the more robust baseline.
aria-live
Purpose
Declares a region whose dynamic changes should be announced to assistive technology.
Syntax
<div id="results" aria-live="polite" aria-atomic="true"></div>
Parameters
off (default), polite (wait for a pause), or assertive (interrupt). Combine with aria-atomic and aria-relevant.
Return / Result
Content changes inside the region are spoken automatically, without moving focus.
Example
<p id="status" aria-live="polite"></p>
<script>
  document.getElementById('status').textContent = 'Draft saved at 14:02.';
</script>
Expected Result
The message is announced when the user pauses, and focus stays where it was.
Common Usage
Search result counts, autosave confirmations, chat transcripts, and validation summaries.
Important Notes
The region must exist before it is updated. Announcements are queued, so rapid updates can stack up — use aria-busy="true" to batch while a long update is in flight. Reserve assertive for genuinely urgent messages.
aria-roledescription
Purpose
Replaces the spoken name of an element's role with a more domain-specific word.
Syntax
<div role="group" aria-roledescription="slide" aria-label="1 of 8">...</div>
Parameters
A short, lower-case, plain-text string. The element must have a valid, non-abstract role.
Return / Result
The screen reader announces the custom term instead of the standard role name.
Example
<section role="group" aria-roledescription="slide" aria-label="3 of 8: Pricing">
  <h2>Pricing</h2>
</section>
Expected Result
Users hear "slide" rather than "group", matching the product's own vocabulary.
Common Usage
Carousels, calendars, and specialised editors where the domain term is clearer than a generic ARIA role.
Important Notes
Use with restraint: it overrides a standard, globally understood term with a term only your product knows, which can confuse users. It does not remove the role — screen readers may still announce both. Avoid translated or invented words, and always give the element an accessible name too.

09Practical Examples

Five worked examples, from the simplest possible use to a realistic component.

Example 1 — Basic Usage

Name an icon-only button so it is not announced as an unnamed control.

<button aria-label="Close">
  <svg aria-hidden="true" focusable="false" width="16" height="16">
    <path d="M2 2 L14 14 M14 2 L2 14" />
  </svg>
</button>

The visual icon carries no text, so aria-label supplies the name. The aria-hidden on the SVG prevents the decorative markup from polluting the announcement, and focusable="false" stops older Edge/IE from putting the SVG in the tab order.

Example 2 — Real-World Usage: a disclosure panel

A "Filters" button that reveals a panel, with the expanded state kept in sync.

<button id="filter-btn" aria-expanded="false" aria-controls="filter-panel">
  Filters
</button>

<section id="filter-panel" hidden>
  <h2>Refine results</h2>
  <label for="min">Minimum price</label>
  <input id="min" type="number" />
</section>

<script>
  const btn = document.getElementById('filter-btn');
  const panel = document.getElementById('filter-panel');

  btn.addEventListener('click', function () {
    const expanded = btn.getAttribute('aria-expanded') === 'true';
    btn.setAttribute('aria-expanded', String(!expanded));
    panel.hidden = expanded;
  });
</script>

Announced as "Filters, button, collapsed" and, after a click, "Filters, button, expanded". Using the native hidden attribute also removes the panel from the accessibility tree and the tab order while it is closed.

Example 3 — Multiple Functions: live search status

Combine a landmark, a searchbox, a live region, and aria-busy.

<search>
  <form role="search" aria-label="Product search">
    <label for="q">Search products</label>
    <input id="q" type="search" aria-describedby="q-hint" />
    <p id="q-hint">Results update as you type.</p>
  </form>
</search>

<p id="status" role="status" aria-live="polite" aria-atomic="true"></p>

<script>
  const input = document.getElementById('q');
  const status = document.getElementById('status');

  input.addEventListener('input', async function () {
    status.setAttribute('aria-busy', 'true');
    const results = await search(input.value);
    status.setAttribute('aria-busy', 'false');
    status.textContent = results.length + ' results found for "' + input.value + '"';
  });
</script>

While the search runs, aria-busy holds announcements; when it finishes, the single status message is spoken politely without stealing focus from the input.

Example 4 — Negative Scenario: an unreachable custom checkbox

What not to do, and why it fails.

<!-- Broken: no role, no name, no keyboard support -->
<div class="checkbox" onclick="toggle()"></div>

<!-- Also broken: role added, but still not focusable or operable -->
<div role="checkbox" aria-checked="false" onclick="toggle()">Subscribe</div>

Neither version is reachable with the keyboard, so a keyboard-only or screen reader user cannot interact with it at all. Adding role="checkbox" changes only what is announced. The correct fix is the native element:

<label>
  <input type="checkbox" />
  Subscribe
</label>

Example 5 — Advanced Usage: accessible tabs

A full tab widget with roving tabindex, arrow-key navigation, and linked panels.

<div class="tabs">
  <div role="tablist" aria-label="Account settings" id="tablist">
    <button role="tab" id="tab-profile" aria-selected="true"  aria-controls="panel-profile">Profile</button>
    <button role="tab" id="tab-billing" aria-selected="false" aria-controls="panel-billing" tabindex="-1">Billing</button>
    <button role="tab" id="tab-team"    aria-selected="false" aria-controls="panel-team"    tabindex="-1">Team</button>
  </div>

  <div role="tabpanel" id="panel-profile" aria-labelledby="tab-profile" tabindex="0">Profile settings</div>
  <div role="tabpanel" id="panel-billing" aria-labelledby="tab-billing" tabindex="0" hidden>Billing settings</div>
  <div role="tabpanel" id="panel-team"    aria-labelledby="tab-team"    tabindex="0" hidden>Team members</div>
</div>

<script>
  const tablist = document.getElementById('tablist');
  const tabs = Array.from(tablist.querySelectorAll('[role="tab"]'));

  function selectTab(tab) {
    tabs.forEach(function (t) {
      const selected = t === tab;
      t.setAttribute('aria-selected', String(selected));
      t.tabIndex = selected ? 0 : -1;
      document.getElementById(t.getAttribute('aria-controls')).hidden = !selected;
    });
    tab.focus();
  }

  tablist.addEventListener('click', function (e) {
    const tab = e.target.closest('[role="tab"]');
    if (tab) selectTab(tab);
  });

  tablist.addEventListener('keydown', function (e) {
    const i = tabs.indexOf(document.activeElement);
    if (i === -1) return;
    let next = null;
    if (e.key === 'ArrowRight') next = tabs[(i + 1) % tabs.length];
    if (e.key === 'ArrowLeft')  next = tabs[(i - 1 + tabs.length) % tabs.length];
    if (e.key === 'Home')       next = tabs[0];
    if (e.key === 'End')        next = tabs[tabs.length - 1];
    if (next) { e.preventDefault(); selectTab(next); }
  });
</script>

Only the selected tab is in the Tab sequence; Left/Right arrows move between tabs and update selection, while Tab moves out of the tablist into the visible panel. aria-selected and hidden stay synchronised with what the user sees.

Testing ARIA from Playwright Because the accessibility tree is exactly what ARIA feeds, Playwright can assert on it: page.getByRole('tab', { name: 'Billing' }), expect(tab).toHaveAttribute('aria-selected', 'true'), expect(button).toHaveAccessibleName('Close'), and toHaveRole(). Automated tools catch roughly a third of accessibility issues — always confirm with a keyboard and a screen reader.

10Before vs After

The most common real-world trade-off is ARIA-patched markup versus a native element. The comparison below is the one that matters most.

Without ARIA (and without native semantics)

<div class="btn" onclick="save()">Save</div>

<span class="toggle" onclick="toggle()">Dark mode</span>

<div class="nav">
  <div class="nav-item" onclick="go('/home')">Home</div>
</div>
  • Screen readers announce anonymous text — "Save", not "Save, button".
  • Nothing is focusable, so keyboard users cannot reach any of it.
  • No Enter/Space activation, no focus ring, no toggle state.
  • Automated tests cannot target these by role.

With the feature (native HTML)

<button type="button" onclick="save()">Save</button>

<label>
  <input type="checkbox" checked />
  Dark mode
</label>

<nav>
  <a href="/home">Home</a>
</nav>
  • Correct roles, names, and states, with no ARIA attributes at all.
  • Focus, keyboard activation, and form participation are built in.
  • Focus indicators and state styling come from the platform.
  • Tests can select by role, name, and label.
The ARIA middle ground The equivalent with ARIA would be <div role="button" tabindex="0">, <div role="switch" aria-checked="true" tabindex="0">, and a role="navigation" container — plus JavaScript for keyboard handling and state. That is strictly more code, more bugs, and no benefit over the native elements. This is why the first rule of ARIA is to avoid ARIA.

12Best Practices

  1. Exhaust native HTML first. If an element already provides the role, state, and behaviour, use it and add no ARIA. This single rule prevents most accessibility defects.
  2. Never change native semantics. Do not turn a <button> into a heading or a heading into a button; replace the element instead.
  3. Give every interactive element an accessible name. An unnamed control is announced as a bare role and is effectively unusable by voice control.
  4. Prefer a visible label over aria-label. When both exist, make the strings match so sighted, screen reader, and voice-control users all refer to the same word.
  5. Keep ARIA state in sync with the UI. Update aria-expanded, aria-selected, and aria-checked in the same code path that changes what the user sees.
  6. Make every ARIA widget keyboard operable. A role without the matching keyboard pattern is a trap; follow the ARIA Authoring Practices patterns.
  7. Reach for aria-hidden only on decorative or duplicated content, and only when it contains nothing focusable.
  8. Use live regions sparingly and politely. Default to role="status"; reserve assertive and role="alert" for urgent, actionable messages.
  9. Choose the least powerful mechanism. Native element > native attribute > ARIA role > ARIA role plus JavaScript. Fewer moving parts means fewer ways to break.
  10. Use landmarks to make the page skimmable. One <main>, a labelled <nav>, and headings in a logical order let non-visual users navigate as efficiently as sighted ones.
  11. Test with a keyboard and a screen reader. Tab through every flow with the mouse untouched, then confirm with NVDA, JAWS, or VoiceOver. Automated tools catch only a fraction of issues.
  12. Treat axe/Lighthouse warnings as findings, not noise. "ARIA attribute is not allowed on this role" almost always indicates a real semantic bug.

13Interview Questions

Beginner Questions

1. What does ARIA stand for, and what are its three building blocks?
Accessible Rich Internet Applications (WAI-ARIA). Its three building blocks are roles (what an element is), states and properties (its current condition, written as aria-* attributes), and keyboard/interaction expectations that the developer must implement.
2. Does adding role="button" to a div make it a button?
Only for assistive technology. It changes what is announced, not what it does. The div is still not focusable, has no Enter/Space activation, and does not render as a button. You must add tabindex and keyboard handlers — or simply use <button>.
3. What is the first rule of ARIA?
If a native HTML element or attribute already provides the semantics and behaviour you need, use it instead of repurposing an element and adding ARIA. In practice: "No ARIA is better than bad ARIA."
4. Which element already has the navigation role, and can you name some other implicit roles?
<nav> maps to navigation. Others include <main> → main, <h1> → heading, <ul> → list, <li> → listitem, <button> → button, and <a href> → link.
5. What is the difference between aria-label and aria-describedby?
aria-label sets the element's name — the short identifier spoken when focus lands. aria-describedby sets the description — extra help text referenced by id, read after a pause or on demand. A field has one name and may have a description.

Intermediate Questions

6. If an element has both aria-label and aria-labelledby, which wins?
aria-labelledby. The accessible name computation checks aria-labelledby first, then aria-label, then native labelling (a <label>, the element's own text, alt, and so on), then the title attribute.
7. Why is aria-hidden="true" on a focusable element a bug?
It removes the element from the accessibility tree but leaves it in the tab order. Keyboard users reach a focus stop that a screen reader cannot describe — "ghost focus" on an invisible control. Remove it from the tab order too (with hidden, display:none, or the inert attribute) or do not hide it at all.
8. What does aria-live="polite" do, and how does it differ from assertive?
Both mark a region whose changes are announced without moving focus. polite waits for the user to be idle before speaking; assertive interrupts immediately. Use polite for statuses and results, assertive only for urgent errors, because interruptions are disruptive.
9. What is roving tabindex, and why do composite widgets use it?
Roving tabindex keeps exactly one item in the tab sequence (tabindex="0") and sets the siblings to tabindex="-1". Arrow keys move focus and the 0 follows the active item. This gives the widget a single tab stop, so users can Tab past it quickly while still navigating inside it — the pattern for tablists, menu bars, and toolbars.
10. Why does role="presentation" on a <ul> also affect its <li> children?
Presentation is inherited by an element's required owned elements. A <ul> requires <li> children, so removing the list semantics removes the listitem semantics with it. Presentation is not inherited by arbitrary descendants — a <div> inside a presentational element keeps its own semantics.

Advanced Questions

11. Describe the accessible name computation order and where each source comes from.
In priority order: (1) aria-labelledby, whose referenced elements' text is concatenated; (2) aria-label; (3) host-language labelling — <label> for form controls, <legend>, <caption>, alt, or the element's text content; (4) the title attribute as a last resort. Descriptions follow the same idea via aria-describedby and title.
12. When would you use aria-activedescendant instead of roving tabindex?
When the items are not focusable and focus must stay on the container — for example a combobox whose text input keeps focus while the highlighted option changes. The container sets aria-activedescendant to the id of the active option, so assistive technology reports it as focused. It needs a stable, unique id per option and constant updates as the highlight moves.
13. Your SPAs toasts never get announced. What are the likely causes?
Most often the region is created and populated in the same render, so no change is observed on an existing live region; alternatively the region is inside a container with aria-hidden, or it is removed from the DOM before the announcement queues. Insert an empty live region on load, flag it aria-busy="true" while updating, then write the text — and leave the region in the DOM after the visual message fades.
14. Why can role="menu" be harmful for site navigation?
It promises application-menu behaviour: arrow-key navigation, Escape to close, focus management, and a specific expected structure of menuitem children. A nav bar of links does not behave that way, so screen reader users are told to expect interactions that do not exist. Use <nav> with a list of links instead.
15. A validator reports "ARIA attribute is not allowed on this role." How do you fix it?
The attribute is not permitted on the element's computed role, so browsers ignore it. Either (a) move the attribute to an element whose role supports it, (b) add the correct role to the element, or (c) — usually best — replace the element with the native HTML element that already carries the semantics and behaviour. Check the role's definition in the WAI-ARIA specification for its allowed states and properties.

16Key Takeaways

  • ARIA adds semantics only: it tells assistive technology what an element is and what condition it is in, but adds no focus, keyboard, or visual behaviour.
  • The first rule is to use native HTML first — "No ARIA is better than bad ARIA."
  • role states what an element is; aria-* attributes describe its current state and are only honoured on roles that allow them.
  • Every interactive element needs an accessible name. Never change native semantics with a contradictory role.
  • Accessible name precedence is aria-labelledby → aria-label → native label → title; a higher-priority source silently overrides the rest.
  • Keep ARIA state synchronised with the visible UI — a stale aria-expanded or aria-checked misleads users more than no attribute at all.
  • Never apply aria-hidden="true" or role="presentation" to focusable content; it creates controls that are reachable but invisible.
  • Live regions must exist before they are updated, and assertive should be rare — default to role="status".
  • Automated tools catch only part of the problem: verify every flow with a keyboard and a real screen reader.
